Requirements Modeling Strategies

Structured analysis
  • มองข้อมูลกับกระบวนการที่แปลงข้อมูลเป็นสิ่งแยกกัน
  • data object ถูก model ด้วย attribute และความสัมพันธ์
  • process ถูก model ให้เห็นว่าแปลงข้อมูลอย่างไรขณะข้อมูลไหลผ่านระบบ
Object-oriented analysis
  • เน้นนิยามคลาส
  • และวิธีที่คลาสทำงานร่วมกันเพื่อสะท้อน requirement ของลูกค้า

Flow-Oriented Modeling

  • แสดงว่า data object ถูกแปลง (transform) อย่างไรขณะเคลื่อนที่ผ่านระบบ
  • ใช้ Data Flow Diagram (DFD) เป็นรูปแบบไดอะแกรม
  • หลายคนมองว่าเป็นแนวทาง "old school" แต่ยังให้มุมมองของระบบที่เป็นเอกลักษณ์ — ใช้เสริม analysis model แบบอื่น

Flow Modeling Notation

External Entity และ Process

External entity
ผู้ผลิตหรือผู้บริโภคข้อมูล — คน องค์กร หรือระบบที่อยู่ภายนอกระบบ และมีปฏิสัมพันธ์กับระบบ (ส่งข้อมูลเข้าหรือรับข้อมูลออก) เช่น a person, a device, a sensor, a computer-based system · data must always originate somewhere and must always be sent to something
Process
ตัวแปลงข้อมูล (data transformer) — เปลี่ยน input เป็น output เช่น compute taxes, determine area, format report, display graph · data must always be processed in some way to achieve system function

logical process ที่ควรใส่ใน DFD (สไลด์ 6-13):

Process ที่…ตัวอย่าง
คำนวณ (perform computations)calculate grade point average
ตัดสินใจ (make decisions)determine availability of ordered products
เรียง กรอง หรือสรุปข้อมูลidentify overdue invoices
จัดข้อมูลให้เป็นสารสนเทศgenerate a report or answer a question
กระตุ้น process อื่นturn on the furnace or instruct a robot
ใช้ข้อมูลที่เก็บไว้create, read, update or delete a record

Data Flow และ Data Store

Data flow
ข้อมูลที่กำลังเคลื่อนที่ (data in motion) — input ของ process, output จาก process หรือการสร้าง/ลบ/อัปเดตข้อมูลใน data store
Data flow packet concept
ข้อมูลที่ควรเดินทางไปด้วยกัน ให้แสดงเป็นdata flow เส้นเดียว ไม่ว่าจะมีเอกสารจริงกี่ชิ้นก็ตาม
Data store
ที่เก็บข้อมูลถาวรที่ process ต้องใช้หรือสร้างขึ้น · flow ที่ออกจาก data store = data retrieval · flow ที่เข้า data store = update หรือ new data

Depicting Business Processes with DFDs

  • business process ซับซ้อนเกินกว่าจะแสดงใน DFD เดียว
  • จึงสร้างลำดับชั้น (hierarchy) ของ DFD หลาย "level" อย่างตั้งใจ
  • สร้าง hierarchy ด้วย Decomposition — child diagram แสดงส่วนหนึ่งของ parent diagram อย่างละเอียดขึ้น

Data Flow Diagramming: Guidelines

  • ทุกไอคอนต้องมีชื่อที่มีความหมาย
  • DFD วิวัฒนาการผ่านหลายระดับรายละเอียด
  • เริ่มต้นด้วย context level diagram (level 0) เสมอ
  • แสดง external entities ที่ level 0 เสมอ
  • ใส่ชื่อ data flow arrow เสมอ

Constructing a DFD:

  1. ทบทวน user scenarios และ/หรือ data model เพื่อแยก data object และใช้ grammatical parse หา "operations"
  2. กำหนด external entities (ผู้ผลิตและผู้บริโภคข้อมูล)
  3. สร้าง level 0 DFD (context diagram)

Context Diagram (Level 0)

  • DFD ระดับบนสุดของทุก process model
  • แสดงบริบทที่ business process อยู่
  • แสดง business process ทั้งหมดเป็นเพียง process เดียว (process 'zero')
  • แสดงexternal entity ทั้งหมดที่รับข้อมูลจากหรือส่งข้อมูลให้ระบบ

สไลด์ 6-35 ถึง 6-37 มีตัวอย่าง DFD Level 0 / 1 / 2 ของ Library Query System ด้วย (ในสไลด์เป็นภาพ) — ใช้ดูประกอบการแตกระดับได้

The Data Flow Hierarchy — Flow Modeling Notes

  • แต่ละ bubble (process) ถูกขยายรายละเอียดจนกว่าจะทำเพียงอย่างเดียว
  • อัตราการขยาย (expansion ratio) ลดลงเมื่อจำนวนระดับเพิ่มขึ้น
  • ระบบส่วนใหญ่ต้องการ 3 ถึง 7 ระดับสำหรับ flow model ที่เพียงพอ
  • data flow เส้นเดียวอาจถูกขยายเมื่อระดับเพิ่ม (data dictionary ให้ข้อมูลรายละเอียด)

Balancing

  • ทำให้ข้อมูลที่แสดงใน DFD ระดับหนึ่งถูกแสดงอย่างถูกต้องในระดับถัดไป
  • data flow บน parent diagram ถูกส่งต่อลงมายัง child diagram
  • child diagram เพิ่ม process ใหม่และ data flow ใหม่ได้

Rules for Data Flows

  • data flow ต้องมีชื่อเสมอ (should never go unnamed)
  • ใน logical modeling ชื่อ data flow ควรอธิบายตัวข้อมูล ไม่ใช่อธิบายการ implement
  • data flow ทุกเส้นต้องเริ่มต้นและ/หรือสิ้นสุดที่ process

Process Specification (PSPEC)

ใช้อธิบายรายละเอียดการทำงานภายในของแต่ละ process — เขียนได้ 5 รูปแบบ:

  • narrative (คำบรรยาย)
  • pseudocode (PDL)
  • equations (สมการ)
  • tables (ตาราง)
  • diagrams and/or charts (แผนภาพ)

ตัวอย่าง PSPEC: Analyze Triangle

process analyze triangle รับ data flow side dimensions of triangle และส่งออก triangle type หรือ error message

แบบ narrative (สไลด์ 7-12)

รับค่า A, B, C ที่เป็นความยาวด้านของสามเหลี่ยม ทดสอบว่าทุกค่าเป็นบวกหรือไม่ ถ้าพบค่าติดลบให้สร้าง error message · จากนั้นประเมินข้อมูลที่ถูกต้องว่าเป็นสามเหลี่ยมได้หรือไม่ และถ้าได้ เป็นชนิดใด — equilateral, isosceles หรือ scalene — แล้วส่งชนิดออกไป

แบบ PDL (สไลด์ 7-13) 
read side dimensions;
if any dimension is negative
  then produce error message;
if the largest dimension is less than
   the sum of the others
  then determine number of equal sides;
    if three sides are equal
      then type is equilateral;
    if two sides are equal
      then type is isosceles;
    if no sides are equal
      then 1) type is scalene;
           2) output triangle type;
else output type = 0,
  indication that no triangle exists;
ลองเล่น: รัน PDL ของ Analyze Triangle ทีละบรรทัด

    ลองค่า 5, 5, 5 · 5, 5, 8 · 1, 2, 3 · −1, 4, 5 แล้วดูว่า PDL เดินไปทางไหน

    Structured English

    ไวยากรณ์ภาษาสำหรับระบุ logic ของ process — อิงจุดแข็งของ structured programming ผสมกับ ภาษาอังกฤษธรรมชาติ (PDL ของ Analyze Triangle ด้านบนก็เขียนในลักษณะนี้: ใช้ if / then / else ร่วมกับประโยคภาษาอังกฤษ)

    Policies และ Decision Tables

    Policy
    ชุดกฎที่กำหนดว่า process หนึ่งต้องทำให้สำเร็จอย่างไร
    Decision table
    การนำเสนอแบบตารางที่ระบุชุดเงื่อนไข (conditions) และการกระทำที่สอดคล้องกัน (actions) ตามที่ต้องใช้ implement policy

    ตัวอย่างประกอบ: นำ logic ของ PDL Analyze Triangle ข้างบนมาเขียนเป็น decision table — แต่ละคอลัมน์คือ 1 กฎ

    กฎ 1กฎ 2กฎ 3กฎ 4กฎ 5
    C1: มีด้านติดลบYNNNN
    C2: ด้านยาวสุด < ผลรวมอีกสองด้าน–NYYY
    C3: จำนวนด้านที่เท่ากัน––320
    A: ผลลัพธ์error messagetype = 0equilateralisoscelesscalene

    ตารางนี้แปลงมาจาก PDL ในสไลด์ 7-13 เพื่อให้เห็นโครงสร้าง conditions/actions — สไลด์ 7-18 "A Simple Decision Table" เป็นภาพตัวอย่างอีกชุดหนึ่ง · "–" = ไม่ต้องพิจารณาเงื่อนไขนั้น

    DFDs: A Look Ahead

    • DFD เป็นส่วนหนึ่งของ analysis model ซึ่ง map ไปสู่ design model
    • A design note: PSPEC หนึ่งอันอาจกลายเป็น "component" หนึ่งหรือหลายตัวใน software design

    Control flow คืออะไร Control flow ใน DFD CSPEC

    Control Flow Modeling

    • control flow แทน "events" และ process ที่จัดการ event
    • Event คือเงื่อนไข Boolean ที่หาได้จาก:
      • ลิสต์ sensor ทั้งหมดที่ซอฟต์แวร์ "อ่าน"
      • ลิสต์ interrupt condition ทั้งหมด
      • ลิสต์ "switch" ทั้งหมดที่ operator กด
      • ลิสต์ data condition ทั้งหมด
      • ทบทวน noun/verb parse ของ processing narrative แล้วดู "control items" ที่อาจเป็น input/output ของ CSPEC
    • control flow คือสัญญาณที่สั่งการ หรือบ่งชี้ว่ามีบางอย่างเกิดขึ้น
    • เกิดขึ้นณ จุดเวลาที่ไม่ต่อเนื่อง (discrete point in time)

    PSPEC vs CSPEC

    PSPEC อธิบายการทำงานภายใน process (narrative, PDL, equation, table, diagram) · CSPEC อธิบายการควบคุมตาม event (state diagram, state transition table, decision table, activation table)

    L3
    1.1.1, 1.1.2 (สองจุด)

    แตกแต่ละ bubble จนทำอย่างเดียว · ส่วนใหญ่ 3–7 ระดับ · สร้าง hierarchy ด้วย decomposition

    04 3 กฎห้ามทำผิดของ Data Flow

    1. data flow ห้ามแตกเป็นหลายเส้นโดยไม่ผ่าน process
    2. data flow ทุกเส้นต้องเริ่มหรือจบที่ process (entity ↔ store ตรงๆ ไม่ได้)
    3. process ต้องมี input ≥ 1 และ output ≥ 1

    flow ต้องมีชื่อเสมอ · ชื่ออธิบายตัวข้อมูล ไม่ใช่วิธี implement

    07 Context Diagram & Balancing

    Context diagram = DFD บนสุด · business process ทั้งหมดเป็น process 'zero' · แสดง external entity ทุกตัว · เริ่มที่ level 0 เสมอ

    Balancing = ข้อมูลระดับหนึ่งแสดงถูกต้องในระดับถัดไป · flow ของ parent ส่งลง child · child เพิ่ม process/flow ใหม่ได้

    01Data Flow Diagram (DFD) ใช้แสดงสิ่งใดเป็นหลัก?

    Flow-oriented modeling represents how data objects are transformed as they move through the system และ DFD คือรูปแบบไดอะแกรมที่ใช้

    02สัญลักษณ์ DFD มีกี่ประเภทหลัก อะไรบ้าง?

    Flow modeling notation ในสไลด์ 6-10 มี 4 ตัว: external entity, process, data flow, data store (วาดได้ทั้งแบบ Yourdon/DeMarco และ Gane/Sarson)

    03"External Entity" ใน DFD คืออะไร?

    External entity = a producer or consumer of data · a person, organization, or system that is external to the system เช่น a person, a device, a sensor, a computer-based system

    04"Process" ใน DFD ทำหน้าที่อะไร?

    Process = a data transformer (changes input to output) — perform computations, make decisions, sort/filter/summarize, organize data into information, trigger other processes, use stored data

    05Context Diagram (Level 0) มีกฎอย่างไรตาม Internal Consistency?

    Internal consistency ของ context diagram: must exist · must contain only one process · at least one input from and one output to an external entity · the process must be numbered 0

    06Detailed DFD ตามกฎ Internal Consistency ควรมีจำนวน process เท่าใด?

    Detailed DFDs: at least one process · no more than seven processes

    07กฎของ Data Flow ข้อใดถูกต้อง?

    Rules for data flows: never go unnamed · all data flows must begin and/or end at a process · data flows should not split into two or more different data flows

    08การแตกไดอะแกรมจากระดับบน (parent) ไปสู่ระดับล่าง (child) ที่มีรายละเอียดมากขึ้น เรียกว่าอะไร?

    สไลด์ 6-17: to build the hierarchy, use Decomposition — child diagrams show a portion of the parent diagram in greater detail · ส่วน balancing คือการตรวจความสอดคล้องระหว่างระดับ

    09"Balancing" ใน DFD หมายถึงอะไร?

    Balancing ensures that information presented at one level of a DFD is accurately represented in the next level DFD — data flows on the parent are carried down to the child

    10ระบบเลขของ process ในระดับ 2 (Level 2) มีรูปแบบอย่างไร?

    Diagram numbering: context = Level 0 · Level 1 = integer (1, 2, 3) · Level 2 = parent number dot unique number (1.1, 1.2) · Level 3 = two dots (1.1.1)

    11PSPEC (Process Specification) ใช้อธิบายอะไร?

    PSPEC ใช้ explain the processes — เขียนได้เป็น narrative, pseudocode (PDL), equations, tables หรือ diagrams/charts เช่น PSPEC ของ Analyze Triangle

    12Structured English คืออะไร?

    Structured English – a language syntax for specifying the logic of a process, based on the relative strengths of structured programming and natural English

    13Decision Table ใช้เพื่อจุดประสงค์ใด?

    Decision table – a tabular form of presentation that specifies a set of conditions and their corresponding actions, as required to implement a policy

    14Control Flow ใน DFD แสดงด้วยสัญลักษณ์ใด?

    Control flows in DFD: represented as a dotted arrow line · ลูกศรบอกทิศ · เขียนชื่อ event ไว้ข้างเส้น

    15Control Flow เป็นตัวแทนของอะไร?

    A control flow represents "events" (Boolean conditions) — a signal that carries out a command or indicates that something has occurred, at a discrete point in time

    16CSPEC (Control Specification) สามารถแสดงในรูปแบบใดได้บ้าง?

    สไลด์ 7-24: CSPEC can be state diagram (sequential spec), state transition table, decision tables, activation tables (combinatorial spec)

    17"Analysis model" (ซึ่งรวม DFD) มีความสัมพันธ์อย่างไรกับ "Design model"?

    สไลด์ 7-19 DFDs: A Look Ahead — analysis model maps into design model และ PSPEC หนึ่งอันอาจกลายเป็น component หนึ่งหรือหลายตัวใน software design

    18หากมี process ที่ไม่มี input หรือ output data flow เลย ถือว่าอย่างไร?

    Don't break DFD rules: processes need to have at least one input data flow and one output data flow — กฎนี้ใช้กับทุก process รวม process 0 ด้วย

    19Data Flow ที่ไหลเข้า/ออกจาก Data Store เรียกว่าอะไรตามลำดับ?

    สไลด์ 6-16: data flows leaving the data store are data retrievals · data flows entering the data store are updates or new data added

    20เหตุใดจึงต้องมีหลายระดับ (levels) ของ DFD สำหรับ business process?

    Business processes are too complex to be shown on a single DFD — จึงสร้าง hierarchy หลาย level ด้วย decomposition
