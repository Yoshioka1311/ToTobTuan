Requirements Analysis คือสะพานเชื่อม

Requirements Analysis ทำอะไร

  • ระบุคุณลักษณะการทำงานของซอฟต์แวร์ (operational characteristics)
  • ขยายความ requirement พื้นฐานที่ได้จาก elicitation
  • ระบุ interface ของซอฟต์แวร์กับส่วนอื่นของระบบ
  • สร้าง model ที่แสดง user scenarios, functional activities, ความสัมพันธ์ของคลาส และ data flow
  • กำหนดข้อจำกัดที่ซอฟต์แวร์ต้องทำตาม
  • มักทำโดย Business Analyst (BA)

วัตถุประสงค์:

  1. อธิบายสิ่งที่ลูกค้าต้องการ
  2. วางรากฐานสำหรับการออกแบบซอฟต์แวร์
  3. กำหนดชุด requirement ที่ตรวจสอบ (validate) ได้เมื่อสร้างซอฟต์แวร์เสร็จ

Scenario-based Models

  • อธิบายว่า actor จะปฏิสัมพันธ์กับระบบอย่างไรในสถานการณ์เฉพาะ
  • เน้น functional requirement จากมุมมองของ actor
  • ใช้ validate requirement กับ stakeholder ได้ดี
  • เทคนิคที่ใช้บ่อย → Use case modelling

"Use-cases are simply an aid to defining what exists outside the system (actors) and what should be performed by the system (use cases)." — Ivar Jacobson

จะเขียนอะไร: การประชุมเก็บ requirement และกลไก RE อื่นๆ ใช้เพื่อระบุ stakeholder, กำหนด scope ของปัญหา, ระบุเป้าหมายการทำงานโดยรวม, จัดลำดับความสำคัญ, ร่าง functional requirement ที่รู้ทั้งหมด และอธิบายสิ่งของ (objects) ที่ระบบจัดการ — เริ่มสร้าง use case ด้วยการลิสต์ function หรือ activity ที่ actor แต่ละตัวทำ

5 ขั้นตอน Requirements Analysis and Modeling

  1. วิเคราะห์ functional requirement เพื่อเข้าใจโครงสร้างของ problem domain
  2. แตกโครงสร้างเป็นส่วนย่อย เพื่อเข้าใจธรรมชาติ ความสัมพันธ์ และหน้าที่ของแต่ละส่วน
  3. ระบุพฤติกรรมและ functional requirement จากมุมมองของ stakeholder
  4. เขียน พัฒนา และปรับปรุง use case diagram และ narrative
  5. ยืนยันว่า requirement model ตอบความต้องการของ stakeholder ทุกฝ่าย

System Concepts for Use Case Modeling

Use case
ลำดับขั้นตอน (scenario) ที่สัมพันธ์กันเชิงพฤติกรรม ทั้งแบบอัตโนมัติและ manual เพื่อทำงานทางธุรกิจหนึ่งงานให้สำเร็จ — อธิบายฟังก์ชันของระบบจากมุมมองผู้ใช้ภายนอก ด้วยคำศัพท์ที่เขาเข้าใจ
Use case diagram
ไดอะแกรมที่แสดงปฏิสัมพันธ์ระหว่างระบบกับระบบภายนอกและผู้ใช้ — บอกด้วยภาพว่าใครจะใช้ระบบ และใช้อย่างไร
Use case narrative
คำอธิบายเชิงข้อความของเหตุการณ์ทางธุรกิจ และวิธีที่ผู้ใช้ปฏิสัมพันธ์กับระบบเพื่อทำงานนั้นให้สำเร็จ

Use Case Relationships

ระดับความสัมพันธ์ระหว่างความหมาย
High-levelAssociationactor ↔ use caseปฏิสัมพันธ์ระหว่าง actor กับ use case
DetailedInheritanceactor ↔ actorย้ายพฤติกรรมร่วมของหลาย actor ไปไว้ที่ abstract actor ร่วมกัน เพื่อลดความซ้ำซ้อน
DetailedIncludesuse case → use caseลดความซับซ้อนของ use case ใหญ่ โดยแยกพฤติกรรมร่วมออกมา
DetailedExtendsuse case → use caseให้พฤติกรรมเสริมที่เป็นทางเลือกจาก base use case

Inheritance (ระหว่าง actor)

เมื่อ actor หลายตัวมีพฤติกรรมร่วมกัน ให้ย้ายพฤติกรรมร่วมไปไว้ที่ abstract actor แล้วให้ actor เดิมสืบทอด เพื่อไม่ต้องลากเส้นซ้ำ

Includes (ระหว่าง use case)

ใช้ลดความซับซ้อนของ use case ขนาดใหญ่ด้วยการแยกพฤติกรรมร่วมออกมา · วาดเป็นลูกศรจาก use case ต้นทาง ชี้ไปยัง use case ที่ถูกใช้ กำกับ <<includes>>

Extends (ระหว่าง use case)

ให้พฤติกรรมเสริมที่เป็นทางเลือก (optional) จาก base use case ที่สมบูรณ์ในตัวเองอยู่แล้ว · วาดเป็นลูกศรจาก use case ที่ขยาย ชี้ไปยัง base use case กำกับ <<extends>>

ทิศลูกศร includes vs extends

Includes: ลูกศรออกจาก use case ต้นทาง (ใหญ่) → ชี้ไปที่ use case ที่ถูกใช้ (พฤติกรรมร่วม) · Extends: ลูกศรออกจาก use case ที่ขยาย (ทางเลือก) → ชี้ไปที่ base use case — ทั้งคู่ใช้เส้นประและกำกับ stereotype

6 ขั้นตอน Use case narrative ตัวอย่างประกอบ: ระบบห้องสมุด

Developing a Use Case — 6 ขั้นตอน

  1. Identify the system boundary — กำหนดว่ากำลัง model ระบบใด แล้ววาดกล่องแทน scope ของระบบ
  2. Identify the actors — ใครจะปฏิสัมพันธ์กับระบบ แบ่งเป็น primary (ใช้ระบบตรงเพื่อบรรลุเป้าหมาย เช่น customer) และ secondary (บทบาทสนับสนุน เช่น payment service)
  3. Identify use cases — ลิสต์งาน/เป้าหมายหลักที่ actor ต้องการ ควรสะท้อน functional requirement (เช่น "Book Ticket", "Generate Report")
  4. Establish relationships between actors and use cases — เชื่อม actor กับ use case ที่เขาเริ่มหรือมีส่วนร่วม และพิจารณาประเภทความสัมพันธ์
  5. Draw a use case diagram — actor นอกกล่อง use case ในกล่อง แสดง association และความสัมพันธ์ให้ชัด
  6. Review and refine — ตรวจว่าครอบคลุม functional requirement ทั้งหมด และ validate กับ stakeholder ว่าครบถ้วนถูกต้อง

Use Case Narrative

คำอธิบายเชิงข้อความแบบละเอียดว่าระบบปฏิสัมพันธ์กับ external entities (actors) อย่างไรเพื่อบรรลุเป้าหมายหนึ่ง — ให้คำอธิบายทีละขั้น และมักเขียนในรูปแบบตาราง

#องค์ประกอบความหมาย
1Use Case Nameชื่อชัดเจน อธิบายได้ — ต้องตรงกับชื่อใน use case diagram

ระบบถูกออกแบบมาเพื่อรองรับการจำหน่ายและจัดการบัตรเข้าสวนสัตว์ ทั้งการซื้อบัตรล่วงหน้าผ่านระบบและการซื้อบัตร ณ จุดจำหน่ายหน้าสวนสัตว์ — ผู้ใช้งานหลัก 3 กลุ่ม:

ผู้ใช้งานสิ่งที่ทำได้ในระบบ (ตามคำอธิบาย)
ผู้เยี่ยมชมเลือกประเภทบัตร (เด็ก / ผู้ใหญ่ / ผู้สูงอายุ) และวันที่เข้าชม → ระบบแสดงราคาตามที่ผู้ดูแลระบบกำหนด → ชำระเงินผ่านบัตรเครดิตหรือ QR Code → เมื่อชำระสำเร็จ ระบบออกตั๋วพร้อม Booking ID และ QR Code · ตรวจสอบรายละเอียดและสถานะของตั๋วได้ · ส่งคำขอยกเลิกตั๋วก่อนวันเข้าชมได้ โดยระบบตรวจเงื่อนไขการคืนเงินและคืนเงินหากเป็นไปตามนโยบาย
เจ้าหน้าที่ขายตั๋วปฏิบัติงาน ณ จุดจำหน่ายหน้าสวนสัตว์ · จำหน่ายตั๋ว (เลือกประเภทบัตร จำนวน วันที่เข้าชม รับชำระเงินผ่านช่องทางที่กำหนด และออกตั๋ว) · ตรวจสอบ แก้ไข หรือยกเลิกรายการตั๋วตามคำร้องขอของผู้เยี่ยมชม โดยคืนเงินตามนโยบาย

07 แนวคิดหลัก

Requirements analysis = สะพาน: requirements specification → analysis model → design model (มักทำโดย BA)

Use case = ลำดับขั้นตอนที่สัมพันธ์เชิงพฤติกรรม (อัตโนมัติ + manual) เพื่อทำงานธุรกิจ 1 งาน

Jacobson: use case ช่วยนิยามสิ่งที่อยู่นอกระบบ (actors) และสิ่งที่ระบบควรทำ (use cases)

แบบฝึกหัด 20 ข้อ

เลือกคำตอบให้ครบแล้วกด "ตรวจคำตอบ" ด้านล่าง ระบบจะเฉลยพร้อมคำอธิบายทุกข้อ

01Use Case คืออะไร?

สไลด์ 4-12: use case – a behaviourally related sequence of steps (scenario), both automated and manual, for the purpose of completing a single business task

02สัญลักษณ์พื้นฐานของ Use Case Diagram ประกอบด้วยอะไรบ้าง?

Basic use case symbols: use case = ellipse · actor = stickman · system boundary = box ที่กำกับชื่อระบบ

03ชื่อของ Use case ควรเริ่มต้นด้วยอะไร?

สไลด์ 4-13 ให้ use case begin with "verb" เช่น Book a ticket, View product

04ความสัมพันธ์แบบ "Association" หมายถึงอะไร?

Association (high-level relationship) represents an interaction between an actor and a use case · ตัวเลือกอื่นคือ inheritance, extends และ includes

05ความสัมพันธ์แบบ "Includes" ใช้เพื่อจุดประสงค์ใด?

Includes simplifies large use case by extracting common behaviours เช่น Checkout includes Scan Item, Calculate Total and Tax, Payment · พฤติกรรมเสริมแบบทางเลือกคือ extends

06ความสัมพันธ์แบบ "Extends" ใช้เพื่อจุดประสงค์ใด?

Extends provides an optional behaviour from the base use case — Registration สมบูรณ์ในตัวเอง และอาจขยายด้วย Get Help On Registration

07ความสัมพันธ์แบบ "Inheritance" ระหว่าง actor มีไว้เพื่ออะไร?

Inheritance: common behavior of multiple actors is moved to a shared abstract actor to avoid redundancy

08Actor แบบ "Secondary" หมายถึงอะไร?

สไลด์ 4-21: actors can be primary (directly use the system to achieve goals, e.g., customer) or secondary (supporting role, e.g., a payment service)

09ขั้นตอนแรกในการพัฒนา Use Case Diagram คือข้อใด?

Developing a use case ขั้น 1) identify the system boundary → 2) actors → 3) use cases → 4) relationships → 5) draw → 6) review and refine

10Use Case Narrative คืออะไร?

สไลด์ 4-23: a detailed textual description of how a system interacts with external entities (actors) to achieve a specific goal — มักเขียนเป็นตาราง

11องค์ประกอบ "Trigger" ใน Use Case Narrative หมายถึงอะไร?

Trigger = the event that initiates the use case · เงื่อนไขก่อนเริ่มคือ precondition และสถานะหลังจบคือ postcondition

12องค์ประกอบ "Postcondition" หมายถึงอะไร?

Postcondition = the state of the system after the use case is completed

13องค์ประกอบ "Exception" หมายถึงอะไร?

Exception = what happens if something goes wrong, such as an error or invalid input · ลำดับปกติคือ scenario

14"Scenario" ใน Use Case Narrative บางครั้งเรียกอีกชื่อว่าอะไร?

Scenario = the typical sequence of interactions between the actor and the system. Sometimes it is called "main flow" or "basic flow"

15Requirements Modeling Approaches ที่เรียนมี 5 ประเภทหลักคือข้อใด?

สไลด์ 4-7 (Pressman): scenario-based models, class models, flow models, behavioral models, data models · ตัวเลือก B คือ process models ของบทที่ 2

16Scenario-based Models เน้นอธิบาย requirement จากมุมมองใด?

Scenario-based models depict requirements from the users' point of view (i.e., actors) และ focus on functional requirements from actors' point of view

17ชื่อของ Use Case ในไดอะแกรม ต้องสอดคล้องกับสิ่งใด?

Use Case Name ใน narrative: a clear, descriptive title. The name must be consistent with the one in a use case diagram

18ตามคำกล่าวของ Ivar Jacobson, Use case มีไว้เพื่อช่วยนิยามอะไร?

"Use-cases are simply an aid to defining what exists outside the system (actors) and what should be performed by the system (use cases)." — Ivar Jacobson

19ขั้นตอนสุดท้ายในการพัฒนา Use Case ("Review and refine") ควรทำอะไร?

6) Review and refine: check if all functional requirements are covered · validate with stakeholders to confirm completeness and accuracy

20Requirements Analysis ทำหน้าที่เป็น "สะพาน" เชื่อมระหว่างอะไร?

สไลด์ 4-4 A Bridge: requirements specification → analysis model → design model
