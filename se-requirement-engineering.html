Requirement Engineering

requirement คือคำอธิบายว่าระบบต้องทำอะไรและมีข้อจำกัดอะไร บทนี้ไล่ตั้งแต่ประเภทของ requirement, feasibility study ไปจนถึง 4 กระบวนการของ requirements engineering: การรวบรวม การเขียนเป็นเอกสาร การตรวจสอบ และการจัดการเมื่อ requirement เปลี่ยน

เนื้อหาแยกตามหัวข้อในสไลด์

Software requirements คืออะไร User vs System Functional vs Non-functional

Software Requirements คืออะไร

  • คำอธิบายบริการ (services) ที่ระบบควรมอบให้ และข้อจำกัด (constraints) ในการดำเนินงานของระบบ
  • สะท้อนความต้องการของลูกค้าสำหรับระบบที่มีวัตถุประสงค์เฉพาะ
  • มักมีนิยามเชิงฟังก์ชันแบบละเอียดและเป็นทางการ

วัสดุประกอบการสอนดัดแปลงจาก Sommerville, Software Engineering (2015) — ตัวอย่างหลักในสไลด์คือระบบข้อมูลผู้ป่วยสุขภาพจิต Mentcare ซึ่งมี stakeholder เช่น patients, doctors, nurses, medical receptionists, IT staff, medical ethics manager, health care managers และ medical records staff

User requirements vs System requirements

User requirements
  • ระบุบริการที่คาดว่าจะมอบให้ผู้ใช้ และข้อจำกัดที่ระบบต้องทำงานภายใต้
  • อาจเป็นข้อความกว้างๆ ไปจนถึงรายละเอียดเจาะจง
System requirements
  • อธิบายฟังก์ชัน บริการ และข้อจำกัดในการดำเนินงานอย่างละเอียด
  • กำหนดสิ่งที่ต้อง implement อย่างแน่ชัด (define exactly what is to be implemented)

Functional vs Non-functional requirements

Functional requirements
  • ระบุบริการที่ระบบต้องให้ — ระบบควรทำอะไร
  • ระบบควรตอบสนองต่อ input เฉพาะอย่างไร
  • ระบบควรทำงานอย่างไรในสถานการณ์ต่างๆ
Non-functional requirements
  • ระบุข้อจำกัดของบริการหรือฟังก์ชัน เช่น response time, compatibility, memory use
  • มักครอบคลุมทั้งระบบ มากกว่าฟีเจอร์เดียว

ตัวอย่าง functional requirements (Mentcare, สไลด์ 3-13):

  • A user shall be able to search the appointments lists for all clinics.
  • The system shall generate each day, for each clinic, a list of patients who are expected to attend appointments that day.
  • Each staff member using the system shall be uniquely identified by his or her eight-digit employee number.
Non-functional ต้องวัดผลได้

สไลด์ 3-15 เน้นว่า non-functional requirement must be measurable and testable — เช่น "handle up to 10,000 concurrent users without significant performance degradation" หรือ "load within 2 seconds for 95% of user requests" (ตัวอย่างจากแบบฝึกหัดในสไลด์ 3-16) มีตัวเลขให้ทดสอบได้ ต่างจาก "should be easy-to-use" ที่ไม่มีเกณฑ์วัด

Feasibility study กระบวนการ RE Elicitation: เป้าหมายและความท้าทาย 6 มิติของ elicitation Interviewing Ethnography เทคนิคอื่น

Feasibility Study

การศึกษาสั้นๆ และเจาะจง ที่ควรทำตั้งแต่ต้นของกระบวนการ RE เพื่อตอบ 3 คำถาม:

  1. ระบบช่วยให้บรรลุเป้าหมายโดยรวมขององค์กรหรือไม่
  2. ระบบทำได้ภายในตารางเวลาและงบประมาณ ด้วยเทคโนโลยีปัจจุบันหรือไม่
  3. ระบบรวมเข้ากับระบบอื่นที่ใช้อยู่ได้หรือไม่
กฎตัดสินใจ

ถ้าคำตอบข้อใดข้อหนึ่งเป็น "ไม่" ก็ไม่ควรเดินหน้าโปรเจกต์ต่อ

กระบวนการ Requirements Engineering (RE)

กระบวนการค้นหา วิเคราะห์ จัดทำเอกสาร และตรวจสอบ software requirements เรียกว่า Requirements Engineering — เป็นกระบวนการวนซ้ำ (iterative) และให้ผลลัพธ์เป็น System requirements document

Requirements Elicitation

เป้าหมาย: เข้าใจงานที่ stakeholder ทำ และวิธีที่ระบบใหม่จะช่วยสนับสนุนงานนั้น — software engineer ทำงานร่วมกับ stakeholder เพื่อหา application domain, work activities, บริการและฟีเจอร์ที่ต้องการ, performance ที่ต้องการ, ข้อจำกัดด้าน hardware ฯลฯ

ความท้าทาย:

  • stakeholder มักไม่รู้ว่าตัวเองต้องการอะไร
  • stakeholder อธิบายสิ่งที่ต้องการได้ยาก
  • stakeholder อาจเรียกร้องสิ่งที่ทำไม่ได้จริง เพราะไม่รู้ว่าอะไรเป็นไปได้
  • stakeholder ต่างกลุ่มกัน มี requirement หลากหลาย และพูดความต้องการต่างรูปแบบกัน

เทคนิคพื้นฐานที่ 1: Interviewing

Elicitation คือการพบ stakeholder หลายแบบเพื่อค้นหาข้อมูลของระบบ — เข้าใจว่าคนทำงานอย่างไร ผลิตอะไร ใช้ระบบอื่นอย่างไร และต้องเปลี่ยนอย่างไรเพื่อรับระบบใหม่ มี 2 วิธีพื้นฐาน: Interviewing และ Observation/Ethnography

Interviewing = คุยกับคนเกี่ยวกับสิ่งที่เขาทำ (แบบ formal หรือ informal) ถามเรื่องระบบที่ใช้อยู่และระบบที่จะพัฒนา — มี 2 แบบ: closed interviews และ open interviews

ข้อจำกัดของการสัมภาษณ์
  • stakeholder อาจใช้ศัพท์เฉพาะ (jargon) ของสายงาน
  • stakeholder คุ้นเคยกับงานจนอธิบายยาก หรือคิดว่าพื้นฐานเกินกว่าจะพูดถึง
  • อาจไม่ได้ผลกับ requirement ระดับองค์กร เพราะมีความสัมพันธ์เชิงอำนาจที่ซ่อนอยู่ระหว่างคนในองค์กร
เคล็ดลับผู้สัมภาษณ์ที่ดี
  • เปิดใจ (be open-minded)
  • หลีกเลี่ยงความคิดที่ตั้งไว้ล่วงหน้า
  • ตั้งใจฟัง
  • กระตุ้นให้เกิดการสนทนา
  • ไม่ถามว่า "tell me what you want"

เทคนิคพื้นฐานที่ 2: Observation / Ethnography

  • เป็นเทคนิคเชิงสังเกต (observational technique) ใช้ทำความเข้าใจ operational process และหา requirement ของซอฟต์แวร์ที่จะรองรับ process นั้น
  • analyst เข้าไปอยู่ในสภาพแวดล้อมการทำงานจริงที่จะใช้ระบบ สังเกตงานประจำวัน และจดงานจริงที่ผู้ใช้ทำ
  • ช่วยค้นพบ implicit requirements ที่สะท้อนวิธีทำงานจริง ไม่ใช่แค่กระบวนการที่องค์กรนิยามไว้เป็นทางการ

เทคนิค elicitation อื่นๆ

  • สุ่มตัวอย่างเอกสาร แบบฟอร์ม และฐานข้อมูลที่มีอยู่ (sampling of existing documentation, forms, and databases)
  • การวิจัยและเยี่ยมชมสถานที่ (research and site visits)
  • แบบสอบถาม (questionnaires)
  • Joint Requirements Planning (JRP)

แต่ละเทคนิคมีจุดแข็งและเหมาะกับสถานการณ์ต่างกัน

Specification คืออะไร Natural language Structured specification User story & acceptance criteria Use cases Prototyping DFD & ERD

Requirements Specification คืออะไร

  • กระบวนการเขียน user และ system requirements ลงในเอกสาร requirement
  • requirement ต้องชัดเจน ไม่กำกวม เข้าใจง่าย ครบถ้วน และสอดคล้องกัน (clear, unambiguous, easy to understand, complete, consistent)
  • ควรเขียนเป็นประโยคที่มีหมายเลขกำกับในภาษาธรรมชาติ อาจมีตารางง่ายๆ และไดอะแกรมที่เข้าใจง่ายประกอบ

ประเภทของ requirements specification: Natural language specification · Structured specifications · Use case specification · Prototyping

แนวทางเขียน Natural Language Specification

  1. กำหนดรูปแบบมาตรฐาน และให้ทุก requirement ใช้รูปแบบนั้น
  2. ใช้ภาษาอย่างสม่ำเสมอเพื่อแยก mandatory (must have) กับ desirable (nice to have) — "Shall" สำหรับ mandatory / "Should" สำหรับ desirable
  3. เน้นข้อความสำคัญด้วย bold, italic หรือสี
  4. หลีกเลี่ยง jargon คำย่อ และ acronym
  5. พยายามระบุเหตุผล (rationale) ของแต่ละ requirement — อธิบายว่าทำไมต้องมีและใครเสนอ

ตัวอย่างในสไลด์ 3-36:

  • The application shall allow users to view their account balance.
  • The application shall send a real-time notification to users via emails.
  • The application shall require users to securely log in using multi-factor authentication (MFA).

User Story และ Acceptance Criteria

User story ใช้บันทึก requirement และกำหนด scope ของฟังก์ชัน รูปแบบ:

ในฐานะ (As a) … บุคคล/ตำแหน่ง/บทบาทในระบบ · ฉันต้องการ (I want) … พฤติกรรมหรือความสามารถในระบบ · เพื่อที่ (So that) … เมื่อสร้างแล้วได้ประโยชน์ / มีคุณค่ากับธุรกิจอย่างไร

user story ถูกวัดผลด้วย เงื่อนไขการยอมรับ (Acceptance Criteria) หรือ Definition of Done (DoD)

Acceptance criteria
เงื่อนไข/เกณฑ์ที่ต้องทำให้สำเร็จ เพื่อให้ user story เสร็จสมบูรณ์และได้รับการยอมรับจาก stakeholder
คุณลักษณะ
เขียนเป็นข้อๆ เนื้อหาชัดเจนไม่กำกวม · ต้องวัดผลได้ (measurable) · มักเขียนแบบ กำหนดให้ (Given) – เมื่อ (When) – จึง (Then) ซึ่งเป็น Gherkin syntax หรือแบบ bullet point

ตัวอย่างจากสไลด์ 3-43 และ 3-44 — ระบบขายตั๋วสวนสัตว์

User story: ในฐานะผู้เข้าชมสวนสัตว์ ฉันต้องการซื้อตั๋วออนไลน์ผ่านเว็บไซต์ เพื่อที่ฉันจะได้ไม่ต้องต่อคิวยาวที่หน้าทางเข้า

#GivenWhenThen
1ผู้เข้าชมเข้าสู่หน้าเว็บขายตั๋วผู้เข้าชมเลือกจำนวนตั๋ว (ผู้ใหญ่/เด็ก)ระบบแสดงราคารวมทั้งหมดให้เห็นทันที
2ผู้เข้าชมเลือกจำนวนตั๋วเรียบร้อยแล้วผู้เข้าชมชำระเงินผ่านช่องทางที่รองรับ (บัตรเครดิต หรือ QR Payment)ระบบยืนยันการชำระเงินสำเร็จ
3การชำระเงินสำเร็จระบบทำการออกตั๋วผู้เข้าชมได้รับอีเมลยืนยันการซื้อตั๋ว พร้อม QR Code
4ผู้เข้าชมมี QR Code ตั๋วจากอีเมลผู้เข้าชมไปที่ทางเข้าสวนสัตว์และสแกน QR Codeระบบตรวจสอบและอนุญาตให้เข้าสวนสัตว์ได้

As a – I want – So that = รูปแบบของ user story · Given – When – Then = รูปแบบของ acceptance criteria

Use Cases

  • อธิบายปฏิสัมพันธ์ระหว่างผู้ใช้กับระบบด้วย graphical model และ structured text
  • ชุดของ use case แทนปฏิสัมพันธ์ทั้งหมดที่เป็นไปได้ใน system requirements
  • บันทึกด้วย high-level use case diagram และแต่ละ use case ควรมีคำอธิบายเชิงข้อความ

องค์ประกอบของ use case diagram: actor (คนหรือระบบอื่น) เป็น stick figure · interaction แต่ละแบบเป็น วงรีที่มีชื่อ (named ellipse) · เส้นเชื่อม actor กับ interaction

Software Requirements Document (SRS)

  • บางครั้งเรียกว่า software requirements specification (SRS)
  • เป็นข้อความทางการ (official statement) ของสิ่งที่นักพัฒนาต้อง implement
  • รวมทั้ง user และ system requirements — user requirements อยู่ในบทนำของ SRS
  • ผู้อ่านหลากหลาย ตั้งแต่ผู้บริหารระดับสูงจนถึงวิศวกรที่พัฒนาซอฟต์แวร์

ทำไมต้องจัดทำเอกสาร requirement

  • requirement ที่ชัดเจนจำเป็นต่อการ design และ implementation
  • ใช้สร้าง test case และ test scenario — โดยเฉพาะระบบใหญ่ที่ทีม test แยกจากนักพัฒนา
  • ใช้ควบคุม scope creep
  • ใช้สร้างเอกสารฝึกอบรม การตลาด และเอกสาร support/maintenance
  • ช่วยแบ่งโปรเจกต์ใหญ่ จัดลำดับ release และบริหารโปรเจกต์ง่ายขึ้น

Requirements Validation

  • กระบวนการตรวจว่า requirement นิยามระบบที่ลูกค้าต้องการจริง
  • สำคัญมาก เพราะ error ในเอกสาร requirement ทำให้ต้องแก้งานย้อนหลังจำนวนมาก (extensive rework costs) ถ้าพบระหว่างพัฒนาหรือหลังระบบใช้งานแล้ว
  • การเปลี่ยน requirement มักหมายถึงต้องเปลี่ยน design และ implementation ด้วย และต้องทดสอบระบบใหม่

Requirements เปลี่ยนได้ — "wicked problems"

เมื่อ requirement วิวัฒนาการ ต้องติดตาม requirement แต่ละข้อ และรักษาลิงก์ระหว่าง requirement ที่พึ่งพากัน เพื่อประเมินผลกระทบของการเปลี่ยนแปลง — กระบวนการนี้เรียกว่า Requirements Management

Requirements Management

กระบวนการทางการสำหรับเสนอการเปลี่ยนแปลง และเชื่อมโยงการเปลี่ยนแปลงเหล่านั้นกับ system requirements — ประกอบด้วย 2 กระบวนการ:

1. Requirements management planning

กำหนดว่าจะจัดการชุด requirement ที่วิวัฒนาการอย่างไร

2. Requirements change management

จัดการข้อเสนอเปลี่ยนแปลงทั้งหมดหลังเอกสาร requirement ได้รับอนุมัติแล้ว

Requirements management planning — ต้องพิจารณา

Requirements identification
requirement แต่ละข้อต้องมีรหัสไม่ซ้ำ เพื่ออ้างอิงข้ามกันและใช้ประเมิน traceability
Change management process
ชุดกิจกรรมที่ประเมินผลกระทบและต้นทุนของการเปลี่ยนแปลง
Traceability policies
นิยามความสัมพันธ์ระหว่าง requirement แต่ละข้อ และระหว่าง requirement กับ system design
Tool support
เครื่องมืออัตโนมัติสำหรับดูแล requirement

Requirements change management — 3 ขั้น

  1. Problem analysis and change specification — ระบุปัญหาหรือข้อเสนอเปลี่ยนแปลง ตรวจว่าถูกต้องหรือไม่ แล้วตัดสินว่ารับหรือถอน
  2. Change analysis and costing — ประเมินการเปลี่ยนแปลงโดยใช้ข้อมูล traceability และความรู้เรื่อง system requirements แล้วประมาณต้นทุนการแก้ไข
  3. Change implementation — แก้ system design และ implementation

Cheat sheet

ประเภท requirement, 4 กระบวนการ RE, เทคนิค elicitation, user story, เกณฑ์ validation และ requirements management ในหน้าเดียว

01 User vs System requirements

UserSystem
บอกอะไรบริการที่ผู้ใช้คาดหวัง + ข้อจำกัดfunction / service / operational constraint อย่างละเอียด
ระดับกว้าง → ละเอียดได้define exactly what is to be implemented

Requirement = คำอธิบาย services ที่ระบบควรให้ + constraints ในการทำงาน

02 Functional vs Non-functional

FunctionalNon-functional
ระบุบริการที่ระบบต้องทำ · ตอบสนอง input / สถานการณ์อย่างไรข้อจำกัดของบริการ เช่น response time, compatibility, memory use
ขอบเขตฟีเจอร์/บริการเฉพาะมักครอบคลุมทั้งระบบ · ต้อง measurable & testable
ตัวอย่าง"A user shall be able to search the appointments lists for all clinics.""handle up to 10,000 concurrent users without significant performance degradation"

เขียนแบบ natural language: Shall = mandatory · Should = desirable

03 4 กระบวนการ RE

  1. Elicitation — เข้าใจงานของ stakeholder
  2. Specification — เขียนลงเอกสาร (natural language, structured, use case, prototype)
  3. Validation — ตรวจว่าตรงที่ลูกค้าต้องการจริง
  4. Change — จัดการเมื่อ requirement เปลี่ยน

iterative · output = system requirements document · ก่อนเริ่มทำ feasibility study (เป้าหมายองค์กร / เวลา-งบ-เทคโนโลยี / integrate ได้ไหม)

04 2 เทคนิค Elicitation

Interviewing
คุยกับคนเรื่องงานที่ทำ · closed / open · ระวัง jargon, คนคุ้นงานจนอธิบายยาก, อำนาจในองค์กร · ห้ามถาม "tell me what you want"
Observation / Ethnography
analyst เข้าไปอยู่ในที่ทำงานจริง สังเกตงานประจำวัน → เจอ implicit requirements

อื่นๆ: สุ่มเอกสาร/ฟอร์ม/ฐานข้อมูล · site visits · questionnaires · JRP

05 User Story + Acceptance Criteria

User story: As a [role] · I want [feature] · So that [benefit]

Acceptance criteria (Gherkin): Given สถานการณ์ · When ผู้ใช้ทำอะไร · Then ผลลัพธ์ของระบบ

ต้องชัดเจน ไม่กำกวม และวัดผลได้ · หรือเรียก Definition of Done (DoD)

07 Requirements Management

requirement เปลี่ยนเพราะปัญหาเป็น "wicked problem" นิยามไม่ครบ + ความเข้าใจ stakeholder เปลี่ยน

  1. Management planning — identification · change management process · traceability policies · tool support
  2. Change management (หลังอนุมัติเอกสาร) — problem analysis & change spec → change analysis & costing → change implementation

แบบฝึกหัด 20 ข้อ

เลือกคำตอบให้ครบแล้วกด "ตรวจคำตอบ" ด้านล่าง ระบบจะเฉลยพร้อมคำอธิบายทุกข้อ

01Software Requirements คืออะไร?

สไลด์ 3-5: software requirements are the descriptions of the services that a system should provide and the constraints on its operations

02User Requirements ต่างจาก System Requirements อย่างไร?

User requirements บอกบริการที่ผู้ใช้คาดหวังและข้อจำกัด (กว้างไปจนละเอียดได้) · System requirements อธิบาย function/service/constraint อย่างละเอียดและ define exactly what is to be implemented

03Functional Requirements ต่างจาก Non-functional Requirements อย่างไร?

Functional = services ที่ระบบต้องให้ และระบบตอบสนอง input/สถานการณ์อย่างไร · Non-functional = constraints on the services เช่น response time, compatibility, memory use มักครอบคลุมทั้งระบบ

04"ระบบต้องรองรับผู้ใช้พร้อมกันได้ถึง 10,000 คนโดยประสิทธิภาพไม่ลดลงอย่างมีนัยสำคัญ" เป็น requirement ประเภทใด?

ประโยคนี้ไม่ได้เพิ่มบริการใหม่ แต่กำหนดข้อจำกัดด้านประสิทธิภาพของระบบทั้งระบบ และวัดผลได้ (10,000 concurrent users) จึงเป็น non-functional

05Feasibility Study มีวัตถุประสงค์หลักเพื่ออะไร?

Feasibility study ตอบ 3 คำถาม: ช่วยเป้าหมายองค์กรไหม · ทำได้ในเวลา/งบด้วยเทคโนโลยีปัจจุบันไหม · integrate กับระบบที่ใช้อยู่ได้ไหม — ถ้าข้อใดตอบว่าไม่ ไม่ควรทำต่อ

06Requirements Engineering (RE) ประกอบด้วย 4 กระบวนการหลักใด?

RE เป็น iterative process ผลลัพธ์คือ system requirements document มี 4 processes: requirements elicitation, specification, validation และ change · Plan/Organize/Monitor/Adjust คือ POMA ของบทที่ 1

07เทคนิคพื้นฐาน 2 แบบของ Requirements Elicitation คือข้อใด?

Two fundamental approaches: (1) interviewing — คุยกับคนเรื่องงานที่ทำ (2) observation or ethnography — ดูคนทำงานจริงว่าใช้ artifact อะไรอย่างไร

08Ethnography ในบริบท requirements elicitation คืออะไร?

Ethnography is an observational technique — analyst immerses himself or herself in the working environment, observe day-to-day work และช่วยค้นพบ implicit requirements ที่สะท้อนวิธีทำงานจริง

09User Story ประกอบด้วยรูปแบบใด?

User story template: ในฐานะ (As a) บทบาท · ฉันต้องการ (I want) ความสามารถ · เพื่อที่ (So that) ได้ประโยชน์อะไร — ส่วน Given-When-Then ใช้เขียน acceptance criteria

10Acceptance Criteria มักเขียนในรูปแบบใด (Gherkin syntax)?

สไลด์ 3-42: acceptance criteria มักเขียนในรูป กำหนดให้ (Given) – เมื่อ (When) – จึง (Then) ซึ่งเป็น Gherkin syntax หรือเขียนเป็น bullet point

11Use Case Diagram ประกอบด้วยองค์ประกอบหลักใดบ้าง?

สไลด์ 3-46: actors (คนหรือระบบอื่น) เป็น stick figures · แต่ละ interaction เป็น named ellipse · lines link the actors with the interaction

12Requirements Prototyping (ด้าน UI) มี 2 ระดับความสมจริงคือข้อใด?

Low fidelity ใช้กระดาษ/คาร์ดบอร์ดแทนหน้าจอและให้คนเลื่อนบอร์ด · High fidelity ใช้เครื่องมืออัตโนมัติ เช่น Visual Basic เขียนหน้าจอและควบคุม logical flow

13Software Requirements Document (SRS) คืออะไร?

SRS is an official statement of what the system developers should implement และรวมทั้ง user และ system requirements (user requirements อยู่ในบทนำของ SRS)

14Requirements Validation ตรวจสอบเกณฑ์ใดบ้าง?

สไลด์ 3-59 และ 3-60 มี 7 เกณฑ์: validity, consistency, completeness, realism, clarity, verifiability และ traceability

15Traceability check ตรวจสอบเรื่องใด?

Traceability: functional requirements correspond and can be traced back to defined system functions · ตัวเลือกอื่นคือ consistency, clarity และ realism ตามลำดับ

16Requirements Management ประกอบด้วย 2 กระบวนการใด?

Requirements management consists of two processes: requirements management planning (วางวิธีจัดการ requirement ที่วิวัฒนาการ) และ requirements change management (จัดการข้อเสนอเปลี่ยนหลังเอกสารอนุมัติแล้ว)

17เหตุใด Requirements จึงต้องมีการจัดการการเปลี่ยนแปลง?

สไลด์ 3-62: problems are "wicked" problems ที่นิยามได้ไม่ครบ → requirement ที่ผูกกับปัญหาอาจไม่สมบูรณ์ และเมื่อความเข้าใจของ stakeholder เปลี่ยน requirement ก็เปลี่ยน

18การเขียน Natural Language Specification ควรใช้คำใดแยกระหว่าง requirement ที่จำเป็นและที่พึงประสงค์?

Guideline ข้อ 2 ในสไลด์ 3-35: use language consistently — "Shall" for mandatory requirements / "Should" for desirable requirements

19Data Flow Diagram (DFD) และ Entity Relation Diagram (ERD) จัดเป็นเทคนิคประเภทใด?

สไลด์ 3-50 และ 3-51 จัด DFD และ ERD ไว้ใต้หัวข้อ "Other types of requirements specification"

20Structured Specification (แบบตาราง) มีฟิลด์ใดบ้าง (ตัวอย่างบางส่วน)?

Structured specification มี 10 ฟิลด์: requirement ID, requirement type, description, rationale, source, input(s), output(s), action, precondition, postcondition
