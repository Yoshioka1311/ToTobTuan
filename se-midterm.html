โจทย์ตัวอย่าง

ระบบตัวอย่างนี้สร้างขึ้นเพื่อฝึก

Canteen Pre-order System และคำตอบทั้งหมดใน workshop ไม่ได้มาจากสไลด์ และไม่ใช่เฉลยของแบบฝึกหัด Zoo Ticketing System — เป็นตัวอย่างที่ทำตามขั้นตอนและกฎในสไลด์ L4 / L6 เพื่อให้เห็นวิธีคิด คำตอบของโจทย์แบบนี้มีได้มากกว่าหนึ่งแบบ ให้ยึดแนวที่อาจารย์สอนในห้องเป็นหลัก

อ่านคำอธิบายระบบ แล้วลองวาด use case diagram บนกระดาษก่อน จากนั้นค่อยกดดูทีละขั้น:

ระบบสั่งอาหารล่วงหน้าของโรงอาหาร (Canteen Pre-order System) ให้ลูกค้าสั่งอาหารจากร้านในโรงอาหารล่วงหน้า แล้วมารับเมื่ออาหารพร้อม ผู้ใช้งานหลักคือ ลูกค้า ร้านค้า และผู้ดูแลระบบ

ลูกค้าสั่งอาหารโดยเลือกร้าน เมนู จำนวน และเวลารับ ระบบแสดงราคารวมตามราคาที่ร้านค้ากำหนด จากนั้นลูกค้าชำระเงินด้วย QR Code ผ่านผู้ให้บริการชำระเงินภายนอก (Payment Gateway) เมื่อชำระเงินสำเร็จ ระบบออกหมายเลขคำสั่งซื้อ (Order ID) ให้ลูกค้า ลูกค้าตรวจสอบสถานะคำสั่งซื้อได้ และยกเลิกคำสั่งซื้อได้ก่อนที่ร้านจะเริ่มทำอาหาร โดยระบบจะตรวจเงื่อนไขและคืนเงินหากเป็นไปตามนโยบาย

ร้านค้าดูรายการคำสั่งซื้อที่เข้ามา อัปเดตสถานะคำสั่งซื้อ (กำลังทำ / พร้อมรับ) และจัดการเมนูกับราคาของร้าน

ผู้ดูแลระบบจัดการบัญชีของร้านค้า และเรียกดูรายงานยอดขาย

วาดทีละขั้น (6 ขั้นตอนจากสไลด์)

กด "ขั้นถัดไป" เพื่อดูว่าแต่ละขั้นเพิ่มอะไรลงในไดอะแกรม
  1. ขั้นที่ 1 — Identify the system boundaryวาดกล่อง แล้วเขียนชื่อระบบ "Canteen Pre-order System" ไว้ในกล่อง ทุกอย่างที่ระบบทำจะอยู่ในกล่องนี้
  2. ขั้นที่ 2 — Identify the actorsหาว่า "ใคร" ใช้ระบบ จากคำนามในโจทย์: ลูกค้า ร้านค้า ผู้ดูแลระบบ เป็น primary actor (ใช้ระบบตรงเพื่อบรรลุเป้าหมาย) · Payment Gateway เป็น secondary actor (บทบาทสนับสนุน) · วาดทุกตัวไว้นอกกล่อง
  3. ขั้นที่ 3 — Identify use casesหา "ทำอะไร" จากคำกริยาในโจทย์ แล้วตั้งชื่อขึ้นต้นด้วย verb: สั่งอาหาร → Place Order · ตรวจสอบสถานะ → Check Order Status · ยกเลิก → Cancel Order · ดูรายการ → View Orders · อัปเดตสถานะ → Update Order Status · จัดการเมนูกับราคา → Manage Menu · จัดการบัญชีร้านค้า → Manage Shop Accounts · เรียกดูรายงาน → View Sales Report · วาดเป็นวงรีในกล่อง
  4. ขั้นที่ 4 — Establish relationships (association)ลากเส้นทึบจาก actor ไปยัง use case ที่เขาเริ่มหรือมีส่วนร่วม: ลูกค้า 3 เส้น · ร้านค้า 3 เส้น · ผู้ดูแลระบบ 2 เส้น
  5. ขั้นที่ 5 — พิจารณา includes / extends แล้ววาดให้ครบการสั่งอาหารต้องชำระเงินทุกครั้ง → Place Order <<includes>> Make Payment (ลูกศรจาก Place Order ชี้ไป Make Payment) · การคืนเงินเกิดเฉพาะเมื่อเข้าเงื่อนไข และ Cancel Order จบได้เองแม้ไม่คืนเงิน → Process Refund <<extends>> Cancel Order (ลูกศรจาก Process Refund ชี้ไป Cancel Order) · Payment Gateway เชื่อมกับสอง use case ที่เกี่ยวกับเงิน
  6. ขั้นที่ 6 — Review and refineไล่อ่านโจทย์ทีละประโยคแล้วชี้ว่าอยู่ตรงไหนของไดอะแกรม: ทุก functional requirement มี use case รองรับหรือยัง · actor ทุกตัวมีเส้นอย่างน้อยหนึ่งเส้นหรือยัง · ชื่อ use case ขึ้นต้นด้วยกริยาทุกอันหรือยัง

ทำไมเลือกแบบนี้ (และทางเลือกอื่นที่เป็นไปได้)

จุดที่ต้องตัดสินใจที่เลือกเหตุผลตามนิยามในสไลด์
Payment Gateway เป็น actor ไหมเป็น secondary actorสไลด์ยกตัวอย่าง secondary actor ว่า "a payment service" — เป็นระบบภายนอกที่สนับสนุน ไม่ได้ใช้ระบบเพื่อเป้าหมายของตัวเอง
ชำระเงิน: includes หรือ extendsincludesเป็นพฤติกรรมที่ Place Order ต้องใช้ทุกครั้ง จึงแยกออกมาเป็น use case ที่ถูกใช้
คืนเงิน: includes หรือ extendsextendsเป็น optional behaviour — เกิดเฉพาะเมื่อเข้านโยบาย และ base use case (Cancel Order) สมบูรณ์ในตัวเอง
ควรใช้ inheritance ไหมไม่ได้ใช้inheritance ใช้เมื่อ actor หลายตัวมีพฤติกรรมร่วมกัน — ในโจทย์นี้ไม่มี use case ที่ actor สองตัวทำซ้ำกัน ถ้าโจทย์บอกว่า "ทั้งร้านค้าและผู้ดูแลระบบดูรายงานได้" จึงค่อยย้ายไปไว้ที่ abstract actor

บางคนอาจรวม View Orders กับ Update Order Status เป็น use case เดียว หรือแยก Manage Menu เป็น Add / Edit / Delete — ไม่ผิด ตราบใดที่ครอบคลุม requirement ครบและใช้สัญลักษณ์ถูก

ใช้โจทย์เดิมจากการ์ด 02 (Canteen Pre-order System) — ลองวาด context DFD บนกระดาษก่อน:

กด "ขั้นถัดไป" เพื่อดูว่าแต่ละขั้นเพิ่มอะไรลงใน context DFD
  1. ขั้นที่ 1 — วาด process เดียวตรงกลาง ใส่เลข 0context diagram แสดงทั้งระบบเป็น process 'zero' เพียงตัวเดียว ตั้งชื่อเป็นชื่อระบบ
  2. ขั้นที่ 2 — วาง external entity รอบๆใครหรือระบบใดส่งข้อมูลเข้า หรือรับข้อมูลออก: ลูกค้า ร้านค้า ผู้ดูแลระบบ และ Payment Gateway · วาดเป็นสี่เหลี่ยม เขียนชื่อทุกกล่อง
  3. ขั้นที่ 3 — ลาก data flow ขาเข้าแต่ละ entity ส่งข้อมูลอะไรให้ระบบ: ลูกค้าส่ง "รายละเอียดคำสั่งซื้อ" และ "คำขอยกเลิก" · ร้านค้าส่ง "ข้อมูลเมนูและราคา" และ "สถานะการทำอาหาร" · ผู้ดูแลระบบส่ง "ข้อมูลบัญชีร้านค้า" · Payment Gateway ส่ง "ผลการชำระเงิน / คืนเงิน" · ทุกเส้นต้องมีชื่อ
  4. ขั้นที่ 4 — ลาก data flow ขาออกระบบส่งอะไรกลับไป: ลูกค้าได้ "ราคารวม + Order ID" และ "สถานะคำสั่งซื้อ / ผลการคืนเงิน" · ร้านค้าได้ "รายการคำสั่งซื้อ" · ผู้ดูแลระบบได้ "รายงานยอดขาย" · Payment Gateway ได้ "คำขอชำระเงิน / คืนเงิน"
  5. ขั้นที่ 5 — ตรวจกับกฎมี process เดียวเลข 0 ✓ · มี input จาก entity และ output ไป entity ✓ · ทุกเส้นมีชื่อที่บอกตัวข้อมูล (ไม่ใช่วิธีส่ง) ✓ · ทุกเส้นแตะ process — ไม่มีเส้นตรงจาก entity ถึง entity ✓ · ไม่มี data store เพราะ data store ต้องอยู่ระหว่าง 2 process ซึ่งระดับนี้มี process เดียว ✓

02 SE Foundation

Software = instructions + data structures + descriptive information (document)

ลักษณะ: engineered ไม่ใช่ manufactured · intangible · labour intensive · แก้ยาก · ไม่ wear out แต่ obsolete ได้

SE (Lethbridge) = แก้ปัญหาลูกค้า · systematic development & evolution · large, high-quality · ภายใต้ cost/time/constraints

5 aspects: processes · methodologies/techniques · metrics · people & teamwork · project coordination/management
Hierarchy: User → Application → OS → Hardware

09 Part 2: Context DFD

4 สัญลักษณ์: external entity · process · data flow · data store

  1. process เดียว เลข 0 = ทั้งระบบ
  2. external entity ครบทุกตัว
  3. ทุก data flow มีชื่อ (ชื่อข้อมูล ไม่ใช่วิธีส่ง)
  4. ทุกเส้นเริ่มหรือจบที่ process
  5. flow ห้ามแตกกลางทาง · process ต้องมี input ≥ 1 และ output ≥ 1

Packet concept: ข้อมูลที่ไปด้วยกัน = เส้นเดียว · เลข: L0 = 0 · L1 = 1, 2, 3 · L2 = 1.1, 1.2

แบบฝึกหัด 20 ข้อ

เลือกคำตอบให้ครบแล้วกด "ตรวจคำตอบ" ด้านล่าง ระบบจะเฉลยพร้อมคำอธิบายทุกข้อ

01บริษัทหนึ่งบอกว่า "ซอฟต์แวร์ของเราก็คือไฟล์โปรแกรมที่รันได้" ตามนิยามในสไลด์ บริษัทนี้มองข้ามองค์ประกอบใดไป?

ซอฟต์แวร์มี 3 ส่วน: instructions, data structures ที่ให้โปรแกรมจัดการข้อมูลได้ และ descriptive information (document) ที่อธิบายการทำงานและการใช้งาน — ไฟล์โปรแกรมเป็นแค่ส่วนแรก

02ข้อใด "ไม่ใช่" คุณลักษณะของซอฟต์แวร์?

สไลด์ระบุว่าซอฟต์แวร์ does not wear out แต่ can be obsolete — เช่น Windows XP ไม่ได้พัง แต่ล้าสมัยในปี 2014

03ข้อใด "ไม่อยู่" ใน 5 aspects ที่ต้องพิจารณาในการพัฒนาและดูแลระบบซอฟต์แวร์ (Tsui and Karam)?

5 aspects: technical and business processes · specific methodologies and techniques · product characterization and metrics · people skills and teamwork · project coordination and management

04PM ได้ Project Plan มาแล้ว และกำลังออกแบบโครงสร้างทีม จ้างคน จัดฝึกอบรม และเริ่มกลไก risk tracking งานช่วงนี้คือขั้นใดของ POMA?

Organizing รับ Project Plan มาแล้ว design organization structure, hire human resources, complete required education and training และ initiate tracking mechanisms

05ข้อมูลสถานะชี้ว่าโปรเจกต์ช้ากว่าแผนมาก ทีมจึงตัดสินใจตัดฟีเจอร์รองออก การกระทำนี้คือข้อใด?

Adjusting มี 3 ด้านที่ปรับได้ (หรือผสมกัน): resources, schedule และ project content — การตัดฟีเจอร์คือการปรับ project content

06ลำดับชั้นของ WBS ตามสไลด์เรียงจากบนลงล่างอย่างไร?

สไลด์ WBS แสดง 4 ระดับ: System name → Module → Function → Task (แตกจากใหญ่ไปเล็ก)

07ใน UI design process phase ใดเป็นการทดสอบว่า interface ทำทุก task ของผู้ใช้ได้ถูกต้อง รองรับ task variation และง่ายต่อการเรียนรู้?

Phase 4 Interface validation: testing the interface, ทุก task ถูกต้อง, รองรับ task variations, ประเมิน easy to use / easy to learn และผู้ใช้ยอมรับว่าเป็นเครื่องมือที่มีประโยชน์

08โปรเจกต์ขนาดเล็ก requirement ชัดเจนและไม่เปลี่ยน ลูกค้าต้องการเอกสารครบถ้วนเพื่อดูแลระยะยาว process model ใดเหมาะที่สุด?

Pros ของ Waterfall: simple, well-suited for small projects with clear & fixed requirements และ strong documentation supports long-term maintenance

09ในโมเดลใดที่ requirement หลักแต่ละตัวถูกพัฒนาแยกกันผ่าน requirement → design → code → unit test แล้วนำมารวมใน "integration bucket" เพื่อทำ system test?

นี่คือ key characteristics ของ Incremental Model (แบบ A) — ต่างจากแบบ B ที่ปล่อยเป็นหลาย release

10Spiral model วนผ่าน 4 quadrant ตามลำดับใด?

ในสไลด์กำกับเลข 1–4: (1) determine objectives, alternatives, constraints (2) evaluate alternatives, identify, resolve risks (3) develop, verify next-level product (4) plan next phase

11ข้อใดจับคู่ตาม Agile Manifesto ได้ถูกต้อง?

Manifesto: individuals and interactions over processes and tools · working software over comprehensive documentation · customer collaboration over contract negotiation · responding to change over following a plan — ตัวเลือกอื่นสลับฝั่ง

12ข้อใด "ไม่ใช่" key characteristic ของ Scrum?

Scrum: iterative development, incremental delivery, customer collaboration, responding to change, cross-functional teams และ minimal documentation — เอกสารหนักเป็นลักษณะของ traditional

13สไลด์สรุปหัวใจของ process model ไว้ด้วย 3 คำใด?

Process models ให้แนวทางประสานและควบคุม task และคนที่ทำ task — สไลด์เน้นว่า *** coordination, tasks, people ***

14"ระบบต้องส่งอีเมลยืนยันให้ผู้ใช้ทันทีหลังสมัครสมาชิกสำเร็จ" เป็น requirement ประเภทใด?

เป็นบริการที่ระบบต้องทำ และบอกว่าระบบตอบสนองต่อสถานการณ์หนึ่งอย่างไร → functional · ถ้าเขียนว่า "ต้องส่งภายใน 5 วินาที" ส่วนนั้นจึงจะเป็น non-functional

15requirement แบบใดที่ "define exactly what is to be implemented"?

System requirements อธิบาย function, service และ operational constraint อย่างละเอียด และกำหนดสิ่งที่ต้อง implement อย่างแน่ชัด ส่วน user requirements อาจเป็นข้อความกว้างๆ

16ทีมสงสัยว่าพนักงานทำงานจริงไม่ตรงกับขั้นตอนที่องค์กรเขียนไว้ และอยากค้นหา requirement ที่ไม่มีใครพูดออกมา ควรใช้เทคนิค elicitation ใด?

Ethnography ให้ analyst เข้าไปอยู่ในที่ทำงานจริงและสังเกตงานประจำวัน จึงพบ implicit requirements ที่สะท้อนวิธีทำงานจริง ไม่ใช่กระบวนการที่นิยามไว้เป็นทางการ

17ข้อใด "ไม่อยู่" ใน 6 dimensions of detailed requirements elicitation?

6 มิติ: individual functionality, business workflow, data and data formats, user interfaces, existing & systems interfaces และ other constraints (performance, reliability ฯลฯ)

18ข้อใดอธิบาย requirements engineering process ได้ถูกต้อง?

RE is an iterative process · output: system requirements document · 4 processes: elicitation, specification, validation, change
