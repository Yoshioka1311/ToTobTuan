Business Needs → Business Processes → Software Development

ซอฟต์แวร์ไม่ได้เริ่มจากโค้ด แต่เริ่มจากความต้องการทางธุรกิจ แล้วไล่ลงมาเป็น 3 ชั้น:

Business needs
แรงขับเคลื่อน (the driving force) — ธุรกิจอยากได้อะไร อยากแก้ปัญหาอะไร
Business processes
การดำเนินงานจริงเพื่อตอบความต้องการ (key focus: How to get work done?) ประกอบด้วย Actors · Tasks or activities · Rules · Inputs and outputs วาดเป็นแบบจำลองได้ด้วย BPMN และอาจมีหรือไม่มีระบบสนับสนุนก็ได้
Software development
ทำให้ business process มีประสิทธิภาพ แม่นยำ และขยายขนาดได้ (efficient, accurate, scalable) และทำให้ process ถูก digitise, automate และ improve ตาม business need

ตัวอย่าง: ระบบจองโต๊ะร้านอาหาร

ร้านอาหารรับจองแบบ manual — ลูกค้าโทรมาแล้วพนักงานจดเอง ร้านมีเป้าหมายลด human error และเพิ่มประสิทธิภาพ

ชั้นในตัวอย่างนี้
Business needอยากได้ระบบจองออนไลน์เพื่อลดการจองทางโทรศัพท์ (ลดการโทร ลดข้อผิดพลาด)
Business processReservation process: ลูกค้าเลือกเวลา → จัดโต๊ะ → ส่งการยืนยัน
Software developmentสร้างแอปจองโต๊ะที่ลูกค้าจองออนไลน์ได้ และระบบจัดการ availability check ให้

ซอฟต์แวร์คืออะไร — 3 องค์ประกอบ

ตาม Pressman (2015) ซอฟต์แวร์ไม่ใช่แค่โปรแกรม แต่มี 3 ส่วน:

  1. ชุดคำสั่ง (instructions) — ให้ feature, function และ performance
  2. โครงสร้างข้อมูล (data structures) — ทำให้โปรแกรมจัดการข้อมูลได้
  3. เอกสารอธิบาย (descriptive information / document) — อธิบายการทำงานและการใช้งานโปรแกรม
จุดที่มักพลาด

เอกสารก็นับเป็นส่วนหนึ่งของซอฟต์แวร์ — ตรงกับนิยามในสรุปท้ายบทที่ว่า Software = programs, data, and documentation

  • จับต้องไม่ได้ (intangible)

นิยาม Software Engineering (Timothy C. Lethbridge)

"A process of solving customers' problems by the systematic development and evolution of large, high-quality software systems within cost, time and other constraints."

แปล: กระบวนการแก้ปัญหาให้ลูกค้าด้วยการพัฒนาและวิวัฒนาการซอฟต์แวร์ขนาดใหญ่คุณภาพสูงอย่างเป็นระบบ ภายใต้ข้อจำกัดด้านต้นทุน เวลา และอื่นๆ

วลีในนิยามหมายถึง
Solving customers' problems>> our goal (เป้าหมาย)
Systematic development and evolution>> engineering (วิศวกรรม)
Large, high-quality software systems>> very complex (ซับซ้อนมาก)
Cost, time and other constraints>> our limitation (ขีดจำกัดของเรา)

5 มุมมองในงานวิศวกรรมซอฟต์แวร์

การพัฒนาและดูแลระบบซอฟต์แวร์ต้องพิจารณา (Tsui and Karam, Essentials of Software Engineering):

  1. กระบวนการทางเทคนิคและธุรกิจ (technical and business processes)
  2. วิธีการและเทคนิคเฉพาะ (specific methodologies and techniques)
  3. การวัดคุณลักษณะ/metric ของผลิตภัณฑ์ (product characterization and metrics for measurements)
  4. ทักษะคนและการทำงานเป็นทีม (people skills and teamwork)
  5. การประสานงานและบริหารโปรเจกต์ (project coordination and management)

ปัจจัยความสำเร็จ / ล้มเหลวของโปรเจกต์

สไลด์ 1-24 วาดโปรเจกต์ซอฟต์แวร์ไว้กับ Scope, Time, Cost, Quality และบอกว่าโปรเจกต์ต้องมี: clear objectives and goals, clear requirements, stakeholder involvement, executive management support, realistic planning และ good management

Key success factors
  • การมีส่วนร่วมของผู้ใช้ (user involvement)
  • การสนับสนุนจากผู้บริหาร (executive management support)
  • requirement ที่ชัดเจน (clear requirement statements)
  • การวางแผนที่ดี (proper planning)
Top failure reasons
  • ขาดข้อมูลจากผู้ใช้ (lack of user input)
  • requirement ไม่สมบูรณ์ (incomplete requirements)
  • requirement เปลี่ยนแปลงบ่อย (changing requirements)

Requirements (สไลด์ 1-27)

Requirements ใช้ define and qualify system กำหนดโดยลูกค้าโดยมีวิศวกรช่วย · Functional = define what must be done · Non-functional = qualify the functional ones · Design constraints = ข้อจำกัดด้าน design/implementation เช่นภาษาโปรแกรม platform

บทบาทในโปรเจกต์ซอฟต์แวร์

ฝั่งลูกค้า (Client side)

Customers
  • กำหนด business needs
  • ให้ทุนโปรเจกต์ (fund the project)
  • อนุมัติผลงานสุดท้าย (approve the final product)
End users
  • ใช้งานซอฟต์แวร์จริง
  • ให้ feedback ด้าน usability และ functionality

ฝั่งพัฒนา (Development side)

บทบาทหน้าที่
Project Manager (PM)วางแผนและบริหารโปรเจกต์, กำหนด scope, จัดตารางงาน, จัดสรรทรัพยากร, ติดตามความคืบหน้า, จัดการความเสี่ยง, ประสาน stakeholder, ทำให้เสร็จทันเวลาและอยู่ในงบ
Business Analyst (BA)รวบรวม (elicit) วิเคราะห์ และตรวจสอบ business/functional/non-functional requirements, จัดทำเอกสาร requirement specification, เป็นสะพานระหว่างลูกค้า/ผู้ใช้กับทีมพัฒนา
System Analyst (SA)แปล requirement เป็น technical specification, ออกแบบสถาปัตยกรรมซอฟต์แวร์ เลือกเทคโนโลยีและ framework, กำหนด coding standard และ architectural pattern
Software Developerimplement feature, เขียนและดูแลโค้ด, ทำ unit test, แก้ defect, review โค้ด, รวม component เข้าด้วยกัน
UX/UI Designerทำ user research, สร้าง persona / wireframe / mockup / prototype, ออกแบบ interface และปรับ usability/UX
QA Engineer / Testerทำ test plan และ test case, ทดสอบ functional และ non-functional, รายงาน defect, ยืนยันว่าแก้บั๊กแล้ว, ดูแลคุณภาพซอฟต์แวร์
BA กับ SA ต่างกันตรงไหน

BA อยู่ฝั่ง "ต้องการอะไร" — รวบรวมและเขียน requirement เป็นสะพานกับลูกค้า · SA อยู่ฝั่ง "จะสร้างอย่างไร" — แปล requirement เป็น technical specification และออกแบบสถาปัตยกรรม

ประเด็นที่ไม่ใช่เทคนิค (Non-technical issues)

Effort estimation and scheduling
ต้องประมาณและประสานงานหลายรายการมากขึ้น (ทั้ง pre-requisite และ co-requisite) — ยิ่งมีรายการมาก ยิ่งต้องพิจารณาความเสี่ยงและความผันแปรมากขึ้น
Assignments and communications
คนมากขึ้นและทักษะหลากหลายขึ้น → ต้องสื่อสารกันมากขึ้น → error และการแก้ไขมากขึ้น

เพิ่มคนเพื่อแก้ปัญหาได้เสมอหรือไม่? สไลด์ 1-35 ชี้ว่าจำนวนเส้นทางการสื่อสารเพิ่มขึ้นเมื่อคนเพิ่ม และโอกาสผิดพลาดก็เพิ่มตาม:

จำนวนคนเส้นทางการสื่อสาร
2 คน1 เส้นทาง
4 คนอาจมีได้ถึง 6 เส้นทาง
6 คนอาจเพิ่มได้ถึง 15 เส้นทาง
ลองเล่น: ลากเส้นระหว่างทุกคู่ของคนในทีม แล้วนับเส้น

คนเพิ่มจาก 2 → 6 (3 เท่า) แต่เส้นทางเพิ่มจาก 1 → 15 (15 เท่า) — นี่คือเหตุผลที่สไลด์บอกว่ายิ่งคนมาก ยิ่งสื่อสารมาก และยิ่งมีโอกาสผิดพลาด

ขนาดและความซับซ้อนของระบบ (Size and complexity)

Breadth (มิติกว้าง — จำนวนมากขึ้น)
  • จำนวน major function
  • feature ในแต่ละ major function
  • interface ระหว่าง feature และ function
  • interface กับระบบภายนอก ("external" systems)
  • จำนวนผู้ใช้พร้อมกันและผู้ใช้ทั้งหมด
Depth (มิติลึก — การเชื่อมโยง)
  • ระดับการซ้อน (amount of nesting)
  • จำนวนความสัมพันธ์แบบลูกโซ่ (number of "chained" relationships)

สไลด์ 1-38 เทียบผังงานที่ทำ task A → B → C ตรงๆ กับผังที่ต้องรอ signal แล้วแตกทางตามค่า a / b / other และมีงานย่อย A2 เพิ่ม — จำนวนงานใกล้กันแต่ผังหลังซับซ้อนกว่าเพราะมีการแตกแขนงและซ้อนกัน

Implementation และ Testing

Coding conventions ครอบคลุม file organization, indentation, comments, declarations, statements, white space, naming conventions, programming practices / principles / rules of thumb และ architectural best practices — หลักปฏิบัติ:

  • Be consistent — ทำให้สม่ำเสมอ
  • Choose names carefully — ตั้งชื่ออย่างระวัง
  • Test before using — ทดสอบก่อนใช้
  • Know the libraries — รู้จัก library ที่ใช้
  • Do code reviews — ทำ code review
Testingความหมาย
Acceptance testingถ้าไม่ผ่าน ลูกค้าปฏิเสธโปรแกรม (client rejects program)
Unit testingโปรแกรมเมอร์ทดสอบทีละชิ้น (on each piece)
Black-boxสมมติว่าไม่รู้โครงสร้างโค้ด เน้นตรวจ data validation
White-boxทดสอบตาม code path ที่เขียนจริง

Project คืออะไร

"A temporary endeavour undertaken to create a unique product, service, or result" — PMBOK® Guide, Sixth Edition (2017)

ความพยายามชั่วคราวที่ทำขึ้นเพื่อสร้างผลิตภัณฑ์ บริการ หรือผลลัพธ์ที่มีลักษณะเฉพาะตัว

Project

ชั่วคราว — จบเมื่อบรรลุวัตถุประสงค์ หรือเมื่อถูกยุติ (terminated)

Operations

งานที่ทำเพื่อรักษาธุรกิจให้ดำเนินต่อไป (work done to sustain the business)

คุณลักษณะของ project (project attributes):

  • มีจุดประสงค์เฉพาะตัว (has a unique purpose)
  • ชั่วคราว (temporary)
  • ขับเคลื่อนการเปลี่ยนแปลง (drive change)
  • สร้างคุณค่า (enable value creation)
  • ต้องการทรัพยากร (require resources)
  • มี customer หรือ sponsor
  • เกี่ยวข้องกับความไม่แน่นอน (involves uncertainty)

ข้อจำกัดของโปรเจกต์ (Triple Constraint)

ทั้งสามต้องสร้างสมดุลกัน (balancing project constraints) — ถ้าเพิ่มอย่างหนึ่งมักกระทบอีกสองอย่าง

Project Management คืออะไร

  • การประยุกต์ความรู้ ทักษะ เครื่องมือ และเทคนิคกับกิจกรรมของโปรเจกต์ เพื่อให้บรรลุ requirement ของโปรเจกต์
  • Project manager มุ่งให้บรรลุ triple constraint (scope, time, cost goals) และอำนวยความสะดวกทั้งกระบวนการให้ตอบความต้องการและความคาดหวังของ stakeholder

Work Breakdown Structure (WBS)

ก่อนวางแผนต้องรู้เป้าหมาย scope และ deliverables ของโปรเจกต์ — WBS เป็นเทคนิคที่ช่วยแตกงาน ขั้นตอนสร้าง:

  1. กำหนด project scope — ระบบจะมีฟังก์ชันอะไรบ้าง
  2. ระบุ major deliverables — แตก scope เป็นส่วนใหญ่ (มักตรงกับ phase การพัฒนาหรือ feature ใหญ่) เช่น Project Management, Requirements Analysis, UI/UX Design, Development, Testing, Deployment, Training & Documentation
  3. แตก deliverable เป็น sub-deliverable — เช่น Development → Login & registration, Book borrow, Book return, Fine calculation
  4. เรียงลำดับงาน — sequential หรือ parallel
  5. ประมาณเวลาของแต่ละงาน
  6. มอบหมายผู้รับผิดชอบแต่ละงาน
  7. วาง timeline ของโปรเจกต์

PERT และ Initial Schedule Estimate

PERT (Program Evaluation and Review Technique) — แผนภาพแสดงความสัมพันธ์และระยะเวลาของงานที่มี dependency กัน ใช้วางแผนตารางเวลาโปรเจกต์ สไลด์ 1-71 มีงาน Task 1, Task 2, Task 3a–3c, Task 4a–4c, Task 5a–5c ต่อกันไปจนถึง End

Gantt Chart

แสดงระยะเวลาและลำดับของงานต่างๆ ตามช่วงเวลาในรูปแบบแท่ง — แต่ละงานคือแท่งหนึ่งบนแกนเวลา เห็นว่างานไหนเริ่ม/จบเมื่อไรและซ้อนกับงานไหน

ลำดับการใช้เครื่องมือวางแผน

WBS แตกงานและได้ task + คน + เวลา → PERT ดู dependency และระยะเวลาระหว่างงาน → Gantt chart วางงานบนแกนเวลาให้เห็นตารางทั้งโปรเจกต์

Project Success

นิยามความสำเร็จของโปรเจกต์ได้หลายแบบ:

  • บรรลุเป้าหมาย scope, time และ cost
  • ลูกค้า / sponsor พอใจ
  • ผลลัพธ์บรรลุวัตถุประสงค์หลัก เช่น ทำเงินหรือประหยัดเงินได้ตามเป้า ให้ผลตอบแทนการลงทุนที่ดี หรือทำให้ sponsor พอใจ

Top 3 success factors (สไลด์ 1-66): adequate funding · staff expertise · engagement from all stakeholders

04 Project & Triple Constraint

05 POMA 4 ขั้นตอน

  1. Planning — requirement, เป้าหมายวัดผลได้, ประมาณ effort/schedule/ทรัพยากร, ความเสี่ยง → Project Plan
  2. Organizing — โครงสร้างองค์กร, จัดทีม, ฝึกอบรม, เริ่มกลไกติดตาม
  3. Monitoring — เก็บสถานะ → วิเคราะห์/ประเมิน → สื่อสารสถานะ
  4. Adjusting — ปรับ resources / schedule / project content

01คำจำกัดความของ Software Engineering โดย Timothy C. Lethbridge เน้นย้ำเรื่องใดเป็นหลัก?

Lethbridge นิยามว่า SE คือ "a process of solving customers' problems by the systematic development and evolution of large, high-quality software systems within cost, time and other constraints" — เป้าหมายคือแก้ปัญหาลูกค้า ทำอย่างเป็นระบบ ภายใต้ข้อจำกัด

02ซอฟต์แวร์ประกอบด้วยองค์ประกอบใดบ้างตามที่เรียน?

ตาม Pressman ซอฟต์แวร์มี 3 องค์ประกอบ: instructions ที่ให้ feature/function/performance, data structures ที่ให้โปรแกรมจัดการข้อมูลได้ และ descriptive information (เอกสาร) ที่อธิบายการทำงานและการใช้งาน

03คุณลักษณะของซอฟต์แวร์ข้อใดถูกต้อง?

สไลด์ Characteristics of Software: developed or engineered, not manufactured · intangible · labour intensive · difficult to make changes · does not wear out · can be obsolete — ข้ออื่นขัดกับรายการนี้ตรงๆ

04ปัจจัยความสำเร็จสำคัญของโปรเจกต์ซอฟต์แวร์ตามรายงาน Chaos & Capers Jones คือข้อใด?

Key success factors ในสไลด์มี 4 ข้อ: user involvement, executive management support, clear requirement statements และ proper planning

05สาเหตุความล้มเหลวอันดับต้นๆ ของโปรเจกต์ซอฟต์แวร์คือข้อใด?

Top failure reasons ในสไลด์: lack of user input, incomplete requirements และ changing requirements

06บทบาทใดทำหน้าที่แปลความต้องการทางธุรกิจเป็น technical specification และออกแบบสถาปัตยกรรมซอฟต์แวร์?

SA แปล business/functional/non-functional requirements เป็น technical specifications ออกแบบสถาปัตยกรรม เลือกเทคโนโลยี และกำหนด coding standard — ส่วน BA รวบรวม/วิเคราะห์ requirement และเป็นสะพานกับลูกค้า

07เมื่อจำนวนคนในทีมเพิ่มขึ้น จำนวนช่องทางการสื่อสารจะเป็นอย่างไร?

สไลด์ยกตัวอย่าง 2 คนมี 1 เส้นทาง, 4 คนมีได้ถึง 6 เส้นทาง, 6 คนมีได้ถึง 15 เส้นทาง — คนเพิ่ม 3 เท่าแต่เส้นทางเพิ่ม 15 เท่า และโอกาสผิดพลาดก็เพิ่มตาม

08Project Management Spectrum ("4P's") ประกอบด้วยอะไรบ้าง?

The Management Spectrum (4P's) = People (roles), Problem (objectives, scope, alternatives, constraints), Process (tasks, milestones, deliverables, QA) และ Project

09นิยามของ "Project" ตาม PMBOK Guide คือข้อใด?

PMBOK: "a temporary endeavour undertaken to create a unique product, service, or result" — งานประจำเพื่อให้ธุรกิจดำเนินต่อไปคือ operations ไม่ใช่ project

10ข้อจำกัดหลักของโปรเจกต์ที่ต้องสร้างสมดุลกันคือข้อใด?

Project constraints (triple constraint) = Scope, Cost, Time — PM ต้องพยายามให้บรรลุทั้งสามอย่างพร้อมกัน

11กระบวนการบริหารโปรเจกต์ซอฟต์แวร์ (POMA) ประกอบด้วย 4 ขั้นตอนใด?

POMA = Project Planning, Project Organizing, Project Monitoring, Project Adjusting

12ในขั้นตอน Monitoring (POMA) มีองค์ประกอบหลัก 3 อย่างคือข้อใด?

3 main components of project monitoring: project status information collection → analysis and evaluation of collected information → presentation and communication of the project status

13Software Project Management Process เหมือนหรือต่างจาก Software Development Process/Life Cycle?

สไลด์ย้ำเป็นหน้าแยกว่า "Software Project Management Process is not the same as Software Development Process or Software Life Cycle"

14Work Breakdown Structure (WBS) มีประโยชน์อย่างไร?

ขั้นตอนสร้าง WBS: กำหนด scope → แตกเป็น major deliverables → sub-deliverables → เรียงลำดับงาน ประมาณเวลา มอบหมายคน และวาง timeline ผลลัพธ์คือ initial schedule estimate

15PERT ใช้เพื่ออะไรเป็นหลัก?

PERT (Program Evaluation and Review Technique) เป็นแผนภาพที่แสดงงานแต่ละงาน ระยะเวลา และลำดับที่งานต้องต่อกัน ใช้วางแผนตารางเวลาของโปรเจกต์

16Gantt chart ใช้แสดงข้อมูลประเภทใดเป็นหลัก?

Gantt chart วางงานแต่ละงานเป็นแท่งบนแกนเวลา จึงเห็นทั้งระยะเวลาและลำดับของงาน

17"Black-box testing" มีลักษณะอย่างไร?

Black-box: assume no knowledge of code, check the data validation · ส่วน white-box ทดสอบตาม code path ที่เขียนจริง

18ตัวชี้วัดคุณภาพซอฟต์แวร์ที่กล่าวถึงมีอะไรบ้าง?

Examples of software quality indicators ในสไลด์มี 5 ตัว: Usability, Efficiency, Testability, Maintainability, Reusability

19Software Process หมายถึงอะไร?

Software Process = the structured set of activities required to develop a software system · ผลลัพธ์สุดท้าย (ระบบที่ deploy + เอกสาร) คือ Software Product

20Business Process ประกอบด้วยองค์ประกอบใดบ้าง?

Components ของ business process: actors, tasks or activities, rules, inputs and outputs — และวาดได้ด้วย BPMN
