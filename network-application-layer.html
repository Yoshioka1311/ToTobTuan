ภาพรวมบท Application Layer และเป้าหมาย

บทนี้อ้างอิงหนังสือ Computer Networking: A Top-Down Approach 9th edition (Kurose & Ross, Pearson 2025) หัวข้อทั้งหมดของบทได้แก่ หลักการของแอปพลิเคชันเครือข่าย (principles of network applications), Web และ HTTP, E-mail (SMTP, IMAP), ระบบ DNS, video streaming และ content distribution networks และ socket programming ด้วย UDP และ TCP

เป้าหมายของบท (Our goals) มี 3 ด้าน

  1. เข้าใจทั้งแนวคิดและการนำไปใช้งานจริงของ application-layer protocols ได้แก่ transport-layer service models, client-server paradigm และ peer-to-peer paradigm
  2. เรียนรู้โปรโตคอลผ่านการศึกษาโปรโตคอลและโครงสร้างพื้นฐานที่ใช้กันแพร่หลาย ได้แก่ HTTP, SMTP, IMAP, DNS, video streaming systems และ CDNs (Content Delivery networks)
  3. เขียนโปรแกรมแอปพลิเคชันเครือข่ายด้วย socket API

ตัวอย่าง network apps: social media · Web · text messaging · e-mail · multi-user network games · streaming stored video (YouTube, Hulu, Netflix) · P2P file sharing · voice over IP · real-time video conferencing (เช่น Zoom) · Internet search · remote login

สถาปัตยกรรม: Client-Server vs Peer-to-Peer

Client-Server paradigm

Server

  • เป็น always-on host เปิดทำงานตลอดเวลา
  • มี permanent IP address (IP ถาวร)
  • มักอยู่ใน data center เพื่อรองรับการขยายตัว (for scaling)

Clients

  • ติดต่อและสื่อสารกับ server
  • อาจเชื่อมต่อเป็นครั้งคราว (intermittently connected)
  • อาจมี dynamic IP address
  • ไม่สื่อสารกันเองโดยตรง

ตัวอย่าง: HTTP (Web), IMAP (Email), FTP

Peer-to-peer (P2P) architecture
  • ไม่มี always-on server
  • end systems ใดๆ สื่อสารกันเองโดยตรง
  • peer ขอใช้บริการจาก peer อื่น และให้บริการตอบแทนแก่ peer อื่นด้วย
  • self scalability — peer ใหม่นำทั้ง service capacity ใหม่ และ service demand ใหม่เข้ามา
  • peer เชื่อมต่อเป็นครั้งคราวและเปลี่ยน IP address ได้ → จัดการซับซ้อน (complex management)

ตัวอย่าง: P2P file sharing [BitTorrent]

สไลด์ภาษาไทยขยายความว่า Client-Server คือรูปแบบที่แบ่งหน้าที่ชัดเจน เครื่อง Client (มือถือ/คอม) ส่งคำขอ (Request) ส่วนเครื่อง Server (ศูนย์ข้อมูลที่เปิด 24 ชม.) ประมวลผลและส่งข้อมูลตอบกลับ (Response) ขณะที่ P2P ไม่มีเครื่องส่วนกลาง ทุกเครื่องในเครือข่ายมีสิทธิ์เท่ากัน เป็นทั้งผู้รับและผู้ปล่อยข้อมูลพร้อมกัน (ยิ่งคนใช้เยอะ ระบบยิ่งเร็ว) ส่วน Blockchain คืองานบนระบบ P2P ผสมคณิตศาสตร์ เปลี่ยนจากคอมพิวเตอร์เครื่องเดียวที่ใครก็แอบแฮกได้ เป็นคอมพิวเตอร์นับล้านเครื่องทั่วโลกที่ช่วยกันถือข้อมูลชุดเดียวกัน

บริการส่วนใหญ่บนอินเทอร์เน็ตใช้ระบบนี้ เพราะควบคุมความปลอดภัยง่าย และผู้ให้บริการเก็บข้อมูลพฤติกรรมผู้ใช้ได้ดี

  • Social Media (LINE, Facebook, Instagram)
  • สตรีมมิ่งความบันเทิง (YouTube, Netflix, Hulu)
  • ธนาคารและการชำระเงิน (Mobile Banking)
  • เกมออนไลน์ยอดฮิต (RoV, Free Fire)
ใช้ P2P เมื่อไร

เมื่อต้องส่งข้อมูลปริมาณมหาศาล หรือต้องการความปลอดภัยสูงแบบกระจายศูนย์ โดยไม่ให้ใครคนเดียวผูกขาดระบบ

  • BitTorrent: แทนที่จะโหลดไฟล์เกม 50 GB จากเว็บตรงๆ (ทำให้เว็บช้า) คอมพิวเตอร์ของผู้ใช้ทั่วโลกที่เปิดโปรแกรมอยู่ต่อท่อ socket คุยตรงหากันเอง ช่วยกันส่งชิ้นส่วนไฟล์เหมือนจิ๊กซอว์จนครบ
  • เงินดิจิทัลและบล็อกเชน (Bitcoin, Ethereum): ไม่พึ่งเซิร์ฟเวอร์ธนาคารกลาง คอมพิวเตอร์ผู้ใช้ทุกคนในเครือข่าย P2P ช่วยกันตรวจสอบและบันทึกบัญชีการโอนร่วมกันอย่างโปร่งใส
  • ส่งไฟล์ระยะใกล้ (Apple AirDrop / Android Quick Share)
  • โทรศัพท์และวิดีโอคอลยุคใหม่ (WebRTC ใน Zoom หรือ Discord)

Process และการสื่อสารระหว่างโปรเซส

นิยาม

Process คือโปรแกรมที่กำลังทำงานอยู่บนโฮสต์ (program running within a host)

ในเครื่องเดียวกัน (Same Host)

สองโปรเซสสื่อสารกันด้วย inter-process communication (IPC) ซึ่งกำหนดและควบคุมโดยระบบปฏิบัติการ (OS)

ข้ามเครื่อง (Different Hosts)

โปรเซสบนโฮสต์ต่างกันสื่อสารด้วยการแลกเปลี่ยนข้อความ (exchanging messages) ข้ามเครือข่าย

Client process คือโปรเซสที่เริ่มต้นการสื่อสาร (initiates communication) ส่วน server process คือโปรเซสที่รอให้ถูกติดต่อ (waits to be contacted)

ข้อควรระวัง

แม้แอปแบบ P2P จะไม่มี always-on server แต่แอปที่ใช้สถาปัตยกรรม P2P ก็ยังมีทั้ง client process และ server process — เพราะในการสื่อสารแต่ละครั้งต้องมีฝ่ายที่เริ่มและฝ่ายที่รอ

ภาพ IPC ในเครื่องเดียว (สไลด์ภาษาไทย): สมมุติในคอมพิวเตอร์มีแอป Chrome (Process A) และแอป Word (Process B) — IPC อยู่ตรงรอยต่อระหว่างโปรแกรม ทำหน้าที่เหมือนสะพานเจาะกำแพงให้ Process A และ B คุยกันได้โดยตรงผ่าน "โต๊ะกลาง" คือ RAM (shared memory) แต่ถ้า Process A ต้องการคุยกับเซิร์ฟเวอร์ต่างประเทศ ข้อมูลจะถูกส่งไม้ต่อลงไปที่ socket (TCP/UDP) เพื่อแปลงเป็น packet วิ่งลงชั้นกายภาพ เช่น สายเคเบิลใยแก้วนำแสงใต้ทะเล (ไทย → อเมริกา) ที่แบ่งช่องความถี่แบบ FDM/OFDM

Socket: ประตูเชื่อมสู่เครือข่าย

โปรเซสส่งและรับข้อความผ่าน socket ของตัวเอง socket เปรียบเสมือนประตู

  1. โปรเซสผู้ส่งผลักข้อความ (message) ออกไปทางประตู (sending process shoves message out door)
  2. เมื่อพ้นประตูไปแล้ว โปรเซสผู้ส่งอาศัยโครงสร้างพื้นฐานฝั่ง transport ที่อยู่อีกด้านของประตู นำข้อความไปส่งถึง socket ของโปรเซสผู้รับ

การสื่อสารหนึ่งครั้งมี socket 2 ตัวเสมอ — ฝั่งละหนึ่งตัว

เหนือ socket controlled by app developer

ชั้น application (process) — นักพัฒนาควบคุม "ฝั่งในบ้าน"

ใต้ socket controlled by OS

transport, network, link, physical — ระบบปฏิบัติการควบคุม "ฝั่งนอกบ้าน"

Addressing processes

โปรเซสจะรับข้อความได้ต้องมีตัวระบุ (identifier) อุปกรณ์โฮสต์แต่ละเครื่องมี IP address ขนาด 32 บิต ที่ไม่ซ้ำกัน คำถามคือ IP address ของโฮสต์ที่โปรเซสนั้นรันอยู่ เพียงพอจะระบุตัวโปรเซสหรือไม่? คำตอบคือไม่พอ เพราะโฮสต์เดียวอาจมีหลายโปรเซสทำงานอยู่พร้อมกัน

  • IP address ทำงานที่ Network Layer (Layer 3) ใช้ระบุตัวตนของเครื่อง/โฮสต์บนเครือข่ายเท่านั้น ไม่ได้ระบุถึงแอปพลิเคชันหรือโปรเซสที่รันอยู่ภายใน
  • หนึ่งเครื่องรันได้หลายโปรเซส: เครื่องที่มี IP เพียง 1 ค่าอาจรัน Web server, SSH daemon และ Database พร้อมกัน IP อย่างเดียวจึงแยกแยะโปรเซสเหล่านั้นไม่ได้
IP Address + Port Number = Exact Process Identifier
ผ่านระบบเครือข่าย (Over the Network)

ต้องระบุคู่กันระหว่าง IP address + หมายเลขพอร์ต (Port Number) รวมถึงโปรโตคอลขนส่ง (TCP หรือ UDP) โดย port (Layer 4) ทำหน้าที่ส่งข้อมูลไปยัง socket ที่ผูกอยู่กับโปรเซสนั้น

ภายในเครื่องโฮสต์เอง (Locally)

ระบบปฏิบัติการกำหนดหมายเลขประจำตัวเฉพาะเรียกว่า Process ID (PID) ให้ทุกโปรเซสที่กำลังทำงาน

เปรียบเทียบ: ป้ายจ่าหน้าพัสดุ (Shipping Label)

IP Address = บ้านเลขที่ (ระบุอุปกรณ์/House) · Port Number = หมายเลขห้อง (ระบุ process/Specific Room)

ตัวอย่างในสไลด์: ส่งข้อมูลไปที่ 128.119.245.12:80 = บ้านเลขที่ 128.119.245.12 ห้องหมายเลข 80 ซึ่งเป็น Web Server (HTTP) ส่วน Mail Server ในภาพใช้ port 25

บริการของ Internet transport protocols: TCP และ UDP

TCP service
  • reliable transport ระหว่างโปรเซสผู้ส่งและผู้รับ
  • flow control: ผู้ส่งจะไม่ส่งจนผู้รับรับไม่ทัน (sender won't overwhelm receiver) — กลไกควบคุมความเร็วการส่งข้อมูล
  • congestion control: ลดความเร็วผู้ส่ง (throttle sender) เมื่อเครือข่ายรับภาระเกิน
  • connection-oriented: ต้องมีการ setup ระหว่าง client process กับ server process ก่อน

ไม่ให้บริการ: timing, minimum throughput guarantee, security

UDP service
  • unreliable data transfer ระหว่างโปรเซสผู้ส่งและผู้รับ

ไม่ให้บริการ: reliability, flow control, congestion control, timing, throughput guarantee, security หรือ connection setup

Securing TCP ด้วย TLS (Transport Layer Security)

ปัญหา: Vanilla TCP & UDP sockets
  • ไม่มีการเข้ารหัส (no encryption)
  • รหัสผ่านแบบ cleartext ที่ส่งเข้า socket วิ่งผ่านอินเทอร์เน็ตแบบ cleartext
  • ผู้อื่นดักจับแพ็กเก็ตแล้วอ่านได้เลยโดยไม่ต้องถอดรหัส
ทางแก้: TLS
  • ให้ encrypted TCP connections
  • data integrity — ยืนยันความถูกต้องของข้อมูล
  • end-point authentication — ยืนยันตัวตนปลายทาง
ข้อควรระวัง: TLS อยู่ชั้นไหน

แม้ชื่อจะมีคำว่า Transport แต่ TLS implemented in application layer — แอปเรียกใช้ TLS libraries ซึ่งใช้ TCP อีกทีหนึ่ง ผลคือ cleartext ที่ส่งเข้า "socket" จะวิ่งผ่านอินเทอร์เน็ตแบบเข้ารหัสแล้ว

ภาพรวมกลไกของชั้นแอปพลิเคชัน (Key Takeaways)

  1. สถาปัตยกรรม (Architecture): แอปพลิเคชันถูกออกแบบให้ทำงานบน End Systems โดยเลือกใช้แบบ Client-Server (พึ่งพาศูนย์กลาง) หรือ P2P (กระจายศูนย์)
  2. การเชื่อมต่อและระบุตัวตน (Sockets & Addressing): Process สื่อสารกันผ่านประตูที่เรียกว่า Socket โดยหาเป้าหมายเจอด้วยการผสาน IP Address เข้ากับ Port Number
  3. การเลือกพาหนะขนส่ง (Transport Protocols): แอปต้องเลือกระหว่าง TCP (ข้อมูลครบถ้วนแน่นอน) หรือ UDP (ส่งเร็วแต่ไม่รับประกัน) ตามความต้องการใช้งานจริง และเสริมความปลอดภัยด้วย TLS

HTTP overview

HTTP = hypertext transfer protocol เป็น application-layer protocol ของเว็บ ทำงานแบบ client/server model

client

browser ที่ร้องขอ (requests), รับ (receives โดยใช้ HTTP) และ "แสดงผล" (displays) Web objects — ตัวอย่างในสไลด์: iPhone ที่รัน Safari browser, PC ที่รัน Firefox browser

server

Web server ส่ง (sends โดยใช้ HTTP) objects กลับเป็น response ต่อ request — ตัวอย่างในสไลด์: server ที่รัน Apache Web server

HTTP ใช้ TCP ตามลำดับนี้

  1. client เริ่ม TCP connection (สร้าง socket) ไปยัง server ที่ port 80
  2. server ยอมรับ (accepts) TCP connection จาก client
  3. แลกเปลี่ยน HTTP messages (application-layer protocol messages) ระหว่าง browser (HTTP client) กับ Web server (HTTP server)
  4. ปิด TCP connection

HTTP is "stateless"

นิยาม

Stateless: server ไม่เก็บข้อมูลใดๆ เกี่ยวกับ request ในอดีตของ client (server maintains no information about past client requests) ทุกคำขอจึงเป็นเรื่องใหม่ทั้งหมด

ทำไมต้อง stateless (aside ในสไลด์)

โปรโตคอลที่เก็บ "state" นั้นซับซ้อน: (1) ต้องเก็บประวัติในอดีต (state) ไว้ (2) ถ้า server หรือ client ล่ม (crash) ภาพของ state ที่แต่ละฝั่งรับรู้อาจไม่ตรงกัน และต้องปรับให้ตรงกันใหม่

สไลด์สรุปว่า การไม่จำสถานะช่วยให้ระบบทำงานได้เร็ว ไม่ซับซ้อน และหากเซิร์ฟเวอร์ล่มก็ไม่เกิดปัญหาข้อมูลสถานะไม่ตรงกัน (เมื่อต้องการให้จำผู้ใช้ได้ ใช้ cookies — ดูการ์ด 03)

HTTP connections 2 แบบ และตัวอย่าง Non-persistent HTTP

Non-persistent HTTP เปิด → ส่ง 1 ชิ้น → ปิด
  1. เปิด TCP connection
  2. ส่ง object ได้อย่างมาก 1 ชิ้นผ่าน connection นั้น
  3. ปิด TCP connection

การดาวน์โหลดหลาย object ต้องใช้หลาย connection (หน้าเว็บมีหลายภาพ ต้องเปิดการเชื่อมต่อใหม่ซ้ำๆ)

Persistent HTTP เปิด → ส่งหลายชิ้น → ปิด
  • เปิด TCP connection ไปยัง server
  • ส่งหลาย object ผ่าน TCP connection เดียวระหว่าง client กับ server นั้นได้
  • ปิด TCP connection

ลดภาระการทำงานของทั้งฝั่ง client และ server

ตัวอย่าง Non-persistent HTTP: ผู้ใช้พิมพ์ URL www.someSchool.edu/someDepartment/home.index ซึ่งเป็นไฟล์ที่มีข้อความและอ้างอิงรูป jpeg 10 รูป

  1. 1a. HTTP client เริ่ม TCP connection ไปยัง HTTP server (process) ที่ www.someSchool.edu port 80
  2. 1b. HTTP server ที่โฮสต์ www.someSchool.edu ซึ่งรอ TCP connection อยู่ที่ port 80 "ยอมรับ" connection และแจ้ง client
  3. 2. HTTP client ส่ง HTTP request message (มี URL) เข้า TCP connection socket บอกว่าต้องการ object someDepartment/home.index
  4. 3. HTTP server รับ request สร้าง response message ที่มี object ที่ขอ แล้วส่งเข้า socket
  5. 4. HTTP server ปิด TCP connection
  6. 5. HTTP client ได้ response ที่มีไฟล์ html แสดงผล html และเมื่อ parse ไฟล์ html ก็พบ jpeg object ที่อ้างอิงอยู่ 10 ชิ้น
  7. 6. ทำขั้นตอน 1–5 ซ้ำสำหรับ jpeg object ทั้ง 10 ชิ้น

RTT (Round Trip Time) คือเวลาที่แพ็กเก็ตขนาดเล็กใช้เดินทางจาก client ไป server และกลับมา เวลาตอบสนองของ HTTP ต่อ 1 object แบบ non-persistent ประกอบด้วย

  • 1 RTT สำหรับเริ่ม TCP connection (Initiate → Acknowledge)
  • 1 RTT สำหรับ HTTP request และรอให้ข้อมูลไม่กี่ byte แรกของ response กลับมา
  • เวลาส่งไฟล์/object จริง (object/file transmission time)
Non-persistent HTTP response time = 2RTT + file transmission time
ข้อควรระวัง

สูตรนี้คือเวลาต่อ object 1 ชิ้น — ต้องเสียเวลาถึง 2 RTT ต่อการดึงข้อมูลเพียง 1 ชิ้น หน้าเว็บในตัวอย่างที่มี base HTML + jpeg 10 รูป จึงเกิดขั้นตอนนี้ซ้ำ 11 ครั้ง

Persistent HTTP (HTTP 1.1)

ปัญหาของ Non-persistent HTTP
  • ใช้ 2 RTTs ต่อ object
  • มี OS overhead สำหรับทุก TCP connection
  • browser มักเปิดหลาย TCP connection ขนานกันเพื่อดึง object ที่อ้างอิงพร้อมๆ กัน
Persistent HTTP (HTTP1.1)
  • server เปิด connection ค้างไว้หลังส่ง response
  • HTTP messages ถัดไประหว่าง client/server คู่เดิมส่งผ่าน connection ที่เปิดอยู่
  • client ส่ง request ทันทีที่เจอ object ที่อ้างอิง
  • ใช้เวลาเพียงประมาณ 1 RTT สำหรับ object ที่อ้างอิงทั้งหมด (ลดเวลาตอบสนองลงครึ่งหนึ่ง)

HTTP request message

HTTP message มี 2 ประเภท คือ request และ response ข้อความ HTTP เป็นแบบ ASCII ซึ่งมนุษย์อ่านเข้าใจได้ (human-readable format) ตัวอย่าง request จากสไลด์

GET /index.html HTTP/1.1\r\n
Host: www-net.cs.umass.edu\r\n
User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10.15; rv:80.0) Gecko/20100101 Firefox/80.0 \r\n
Accept: text/html,application/xhtml+xml\r\n
Accept-Language: en-us,en;q=0.5\r\n
Accept-Encoding: gzip,deflate\r\n
Connection: keep-alive\r\n
\r\n
request line
บรรทัดแรก ระบุคำสั่ง (method เช่น GET, POST, HEAD), เป้าหมาย (URL) และเวอร์ชัน
header lines
ข้อมูลเพิ่มเติมเกี่ยวกับ client เช่น เครื่องผู้ใช้/เบราว์เซอร์ (User-Agent) หรือภาษาที่รองรับ (Accept-Language)
\r\n
\r = carriage return character · \n = line-feed character ใช้ปิดท้ายทุกบรรทัด
\r\n ต้นบรรทัด
carriage return + line feed ที่ต้นบรรทัด (บรรทัดว่าง) บอกว่าจบส่วน header linesแล้ว

รูปแบบทั่วไป (general format): request line = method sp URL sp version cr lf · header lines = header field name : value cr lf (หลายบรรทัด) · บรรทัดว่าง cr lf · ตามด้วย entity body

Methodหน้าที่ (ตามสไลด์)
GETร้องขอข้อมูลจากเซิร์ฟเวอร์ และใช้ส่งข้อมูลไปเซิร์ฟเวอร์ได้ด้วยการใส่ user data ไว้ใน URL field ของ GET request ต่อจากเครื่องหมาย ? เช่น www.somesite.com/animalsearch?monkeys&banana
POSTเว็บเพจมักมี form input — user input ถูกส่งจาก client ไป server ไว้ใน entity body ของ HTTP POST request message (ข้อมูลจึงถูกซ่อนไว้ใน entity body)
HEADขอเฉพาะ headers ที่จะได้กลับมาถ้าร้องขอ URL นั้นด้วย GET โดยไม่ต้องโหลดไฟล์จริง (ใช้เช็คสถานะหรือลิงก์)
PUTอัปโหลดไฟล์ (object) ใหม่ขึ้น server และแทนที่ไฟล์ที่มีอยู่ ณ URL ที่ระบุทั้งหมดด้วยเนื้อหาใน entity body

Maintaining user/server state: cookies

Cookies คือกลไกที่นำมาแก้จุดอ่อนของ HTTP ที่เป็น stateless (ไม่มีความจำ) เพื่อให้ระบบจำได้ว่าผู้ใช้คือใครและกำลังทำอะไรอยู่ในการรับ-ส่งข้อมูลแต่ละครั้ง การสร้าง state ด้วย cookies มี 4 องค์ประกอบ

  1. Header ใน HTTP Response: server ส่ง header Set-Cookie: กลับไปเพื่อมอบรหัสประจำตัว (Cookie ID) ให้ browser
  2. ไฟล์ Cookie ฝั่ง Client: browser บันทึก Cookie ID นั้นไว้บนเครื่องผู้ใช้
  3. Header ใน HTTP Request: เมื่อคลิกหน้าถัดไป browser แนบ header Cookie: พร้อมรหัสประจำตัวกลับไปหา server โดยอัตโนมัติ
  4. Database ฝั่ง Backend: server นำ Cookie ID ที่ได้รับไปค้นในฐานข้อมูลว่าผู้ใช้คนนี้คือใคร และมีข้อมูลสถานะอะไรค้างไว้

ตัวอย่างในสไลด์ (Amazon): client มี cookie file ของ ebay (8734) อยู่แล้ว เมื่อส่ง HTTP request ปกติไปยัง Amazon server ครั้งแรก server สร้าง ID 1678 ให้ผู้ใช้ สร้าง entry ใน backend database แล้วตอบกลับด้วย set-cookie: 1678 — cookie file ของ client จึงมีทั้ง ebay 8734 และ amazon 1678 ต่อมา request ถัดไปแนบ cookie: 1678 ไปด้วย server ทำ cookie-specific action (เข้าถึงข้อมูลผู้ใช้) และแม้ผ่านไปหนึ่งสัปดาห์ request ใหม่ก็ยังแนบ cookie: 1678 ให้ server จำผู้ใช้ได้

ประโยชน์การใช้งานหลัก: Session Management (จำการล็อกอิน ไม่ต้องพิมพ์รหัสผ่านใหม่ทุกครั้งที่เปลี่ยนหน้า) · Shopping Cart (จำสินค้าในตะกร้า) · User Preferences (จำการตั้งค่า เช่น ภาษา หรือโหมดมืด/สว่าง) · Tracking / Recommendation (บันทึกพฤติกรรมเพื่อแสดงโฆษณาหรือเนื้อหาที่เกี่ยวข้อง)

หมายเหตุ: Cookie ID แบบปลอดภัย

อ้างอิง RFC 4122 / RFC 9562 — การสร้าง Cryptographically Secure UUID ทำได้ด้วยตัวสร้างเลขสุ่มระดับงานเข้ารหัส (CSPRNG — Cryptographically Secure Pseudo-Random Number Generator) เพื่อสร้าง UUID version 4 (UUID ที่เกิดจากการสุ่ม 128 บิต)

Cookies กับการติดตามพฤติกรรม (tracking) และความเป็นส่วนตัว

First-party cookie

มาจากเว็บไซต์ที่ผู้ใช้เลือกเข้าเอง (ผู้ส่ง base html file) — เป็นประโยชน์ เช่น จำสินค้าในตะกร้า แต่เว็บก็ใช้บันทึกประวัติการค้นหา การคลิก หรือเวลาที่ใช้ในแต่ละหน้า เพื่อสร้างโปรไฟล์ความสนใจของผู้ใช้

Third-party cookie

มาจากเว็บที่ผู้ใช้ไม่ได้เลือกเข้า เช่น บริษัทโฆษณาที่ฝังโค้ดไว้ ถ้าหลายเว็บฝังโค้ดจากบริษัทเดียวกัน บริษัทนั้นใช้ Cookie ID เดิมตามรอยผู้ใช้ไปทุกเว็บ รู้ว่าเข้าเว็บอะไรบ้าง แล้วใช้ทำโฆษณาเจาะจงเป้าหมาย (Targeted Ads)

ตัวอย่างในสไลด์ (NY Times + AdX):

Web caches (aka proxy servers)

เป้าหมาย (Goal)

ตอบสนอง request ของ client โดยไม่ต้องไปถึง origin server (satisfy client requests without involving origin server)

  1. ผู้ใช้ตั้งค่า browser ให้ชี้ไปที่ Web cache (local)
  2. browser ส่ง HTTP request ทั้งหมดไปที่ cache
  3. ถ้า object อยู่ใน cache: cache ส่ง object กลับให้ client ทันที
  4. ถ้าไม่มี: cache ขอ object จาก origin server, เก็บ object ที่ได้ไว้ใน cache แล้วจึงส่งกลับให้ client

Web cache ทำหน้าที่เป็นทั้ง client และ server — เป็น server ของ client ที่ร้องขอ และเป็น client ของ origin server

ทำไมต้องทำ Web caching

(1) ลดเวลาตอบสนอง เพราะ cache อยู่ใกล้ client กว่า (2) ลด traffic บน access link ขององค์กร (3) อินเทอร์เน็ตเต็มไปด้วย cache ทำให้ผู้ให้บริการเนื้อหารายเล็ก ("poor" content providers) ส่งเนื้อหาได้มีประสิทธิภาพขึ้น — มีเซิร์ฟเวอร์หลักเครื่องเดียวก็รองรับผู้ใช้พร้อมกันจำนวนมากได้

server บอก cache ว่า object นี้เก็บ cache ได้แค่ไหนผ่าน response header เช่น Cache-Control: max-age=3600 = ให้เก็บไฟล์นี้ไว้ได้ 3,600 วินาที (1 ชั่วโมง) ส่วน no-cache = ต้องยิงไปถาม server ก่อนทุกครั้ง

ตำแหน่ง cacheอยู่ที่ไหนหน้าที่
1. Client-Side / Browser Cacheดิสก์หรือ RAM ของเครื่องผู้ใช้เก็บรูป, CSS, JS ของเว็บที่เคยเปิด เข้าเว็บเดิมซ้ำจะโหลดทันทีโดยไม่ต้องยิง request ออกไป
2. Institutional Network / Forward Proxyใน LAN ของบริษัท มหาวิทยาลัย องค์กร (ก่อนถึง Access Router)ดัก HTTP request ในองค์กร ถ้ามีคนเคยโหลดไฟล์แล้ว คนอื่นดึงจาก cache ได้ทันทีโดยไม่ต้องวิ่งออก access link
3. ISP Edge / CDN CacheEdge Node ของ ISP หรือ CDN (เช่น Cloudflare, Akamai)กระจายคลังข้อมูลไว้ใกล้ผู้ใช้ทั่วโลก ลด RTT ส่งข้อมูลถึงผู้ใช้เร็ว
4. Server-Side / Reverse Proxy Cacheด้านหน้า Origin Server ใน Data Center หรือ Cloudรับภาระส่งไฟล์คงที่ (Static Assets) แทน ไม่ให้ Web Server/Database ทำงานหนักเกินไป
Forward Proxy

ตั้งอยู่ฝั่ง client ช่วยซ่อน IP address ของผู้ใช้ บล็อกเว็บไม่เหมาะสม หรือทำ web caching ภายในองค์กร

Reverse Proxy

ตั้งอยู่ฝั่ง server ช่วยรับ traffic ปริมาณมาก กระจายภาระงาน (Load Balancing) ปกป้องเซิร์ฟเวอร์หลักจากการโจมตี และ cache ไฟล์คงที่

ลักษณะร่วมของ proxy server คือเป็นตัวกลางส่งต่อคำขอ (Intermediary) รับ request จาก client ส่งต่อไป destination server แล้วนำ response ส่งกลับให้ผู้ใช้

Average Delay = (Hit Rate × Delay_Hit) + (Miss Rate × Delay_Miss)
  1. กรณี cache hit ภายในองค์กร (40% หรือ 0.4): ดึงข้อมูลจาก web cache ใน LAN → DelayHit ≈ 0 วินาที (ระดับมิลลิวินาที น้อยจนตัดทิ้งได้)

  4. รวม: Average Delay = (0.4 × 0) + (0.6 × 2.065) = 0 + 1.239 ≈ 1.24 วินาที (ถ้าปัด transmission delay ออก คิดแค่ RTT 2 วินาที จะได้ 0.6 × 2 = 1.2 วินาที)

    HTTP/2

    Key goal

    ลด delay ของ HTTP request ที่มีหลาย object (decreased delay in multi-object HTTP requests)

    HTTP1.1 นำ multiple, pipelined GETs over single TCP connection มาใช้ — browser รัวส่ง GET หลายอันไปพร้อมกันบน TCP connection เดียวได้ ไม่ต้องรอ response ทีละอันเหมือนยุค HTTP/1.0 แต่มีปัญหา

    • server ตอบ ตามลำดับที่ request มาถึง (FCFS: first-come-first-served) เท่านั้น
    • ด้วย FCFS object เล็กอาจต้องรอหลัง object ใหญ่ → เรียกว่า head-of-line (HOL) blocking
    • loss recovery (retransmit TCP segments ที่หาย) ทำให้การส่ง object หยุดชะงัก — ทุกอย่างวิ่งบน TCP เส้นเดียว เมื่อ packet หาย TCP ระงับการส่งทั้งหมดไว้เพื่อรอ retransmission ไฟล์อื่นในคิวจึงติดขัด (stall) ตาม

    HTTP/2 [RFC 7540, 2015] เพิ่มความยืดหยุ่นให้ server ในการส่ง object โดยเปลี่ยนมาใช้ multiplexing หั่นไฟล์เป็นเฟรมเล็กๆ ส่งสลับกันได้

    • methods, status codes และ header fields ส่วนใหญ่ไม่เปลี่ยนจาก HTTP 1.1 (ยังใช้ GET, POST, 200, 404) ผู้พัฒนาจึงไม่ต้องเขียนโค้ดเว็บใหม่
    • ลำดับการส่ง object ขึ้นกับ priority ที่ client กำหนด ไม่จำเป็นต้อง FCFS
    • push object ที่ยังไม่ถูกขอไปให้ client ล่วงหน้า
    • แบ่ง object เป็น frames และจัดตารางส่ง frame เพื่อบรรเทา HOL blocking

    HTTP/2 to HTTP/3 และ QUIC

    HTTP/2 over single TCP connection ยังมีข้อจำกัด

    • แก้ HOL blocking ได้ แต่ยังติดปัญหาตอน retransmission เมื่อแพ็กเก็ตสูญหาย เพราะข้อมูลของ HTTP/2 ยังส่งในสาย TCP เส้นเดียว จึงเกิดแนวคิดที่จะเพิ่มการส่งให้มากกว่า 1 ทาง
    • no security over vanilla TCP connection

    HTTP/3: เพิ่ม security และ error-control / congestion-control แยกต่อ object (more pipelining) โดยวิ่งบน UDP

    • connection establishment: reliability, congestion control, authentication, encryption และ state สร้างเสร็จภายใน 1 RTT

    SMTP (RFC 5321)

    • ใช้ TCP เพื่อส่งข้อความอีเมลอย่างเชื่อถือได้ จาก client (mail server ที่เริ่ม connection) ไปยัง server ที่ port 25
    • direct transfer: server ผู้ส่ง (ทำตัวเป็น client) ส่งตรงไปยัง server ผู้รับ
    • การส่งมี 3 phases: SMTP handshaking (greeting) → SMTP transfer of messages → SMTP closure
    • ทำงานแบบ command/response (เหมือน HTTP) — commands เป็น ASCII text, response เป็น status code และ phrase

    ลำดับบน timeline ในสไลด์: "client" SMTP server เริ่ม TCP connection (ใช้ 1 RTT) → "server" ตอบ 220 (เซิร์ฟเวอร์พร้อมให้บริการ) → client ส่ง HELO → server ตอบ 250 Hello (จบ SMTP handshaking) → เข้าสู่ SMTP transfers ซึ่งมี response อย่าง 354 Start mail input

    6. Bob เรียก user agent ของเขาเพื่ออ่านข้อความ

    มนุษย์มีตัวระบุหลายแบบ (เลขประจำตัว, ชื่อ, เลขพาสปอร์ต) อุปกรณ์บนอินเทอร์เน็ตก็เช่นกัน: IP address (32 bit) ใช้ระบุที่อยู่ของ datagrams และ "name" เช่น cs.umass.edu ใช้โดยมนุษย์ คำถามคือจะจับคู่ระหว่าง IP address กับชื่อ (และกลับกัน) อย่างไร?

    นิยาม: Domain Name System (DNS)

    (1) distributed database ที่สร้างเป็นลำดับชั้นของ name servers จำนวนมาก (2) application-layer protocol ที่ hosts และ DNS servers สื่อสารกันเพื่อ resolve ชื่อ (แปล address/name)

    ข้อสังเกต: เป็นฟังก์ชันแกนหลักของอินเทอร์เน็ต แต่ทำเป็น application-layer protocol — ความซับซ้อนอยู่ที่ "edge" ของเครือข่าย · สไลด์สรุประบุว่า DNS ทำงานผ่าน UDP port 53 (เน้นความเร็ว)

    DNS services
    • hostname-to-IP-address translation
    • host aliasing (canonical, alias names)
    • mail server aliasing
    • load distribution — replicated Web servers: หลาย IP address ตรงกับชื่อเดียว
    Q: ทำไมไม่ทำ DNS แบบรวมศูนย์?
    • single point of failure
    • traffic volume
    • distant centralized database
    • maintenance

    A: ไม่ scale! — DNS servers ของ Comcast อย่างเดียวรับ 600B DNS queries/day และของ Akamai 2.2T DNS queries/day

    DNS: distributed, hierarchical database

    ลำดับชั้นมี 3 ระดับ: Root DNS Servers → Top Level Domain (.com, .org, .edu DNS servers …) → Authoritative (yahoo.com, amazon.com, pbs.org, nyu.edu, umass.edu DNS servers …)

    ตัวอย่าง (1st approximation): client ต้องการ IP address ของ www.amazon.com

    1. client ถาม root server เพื่อหา .com DNS server
    2. client ถาม .com DNS server เพื่อหา amazon.com DNS server
    3. client ถาม amazon.com DNS server เพื่อได้ IP address ของ www.amazon.com
    Root name servers
    จุดติดต่อทางการสุดท้าย (contact-of-last-resort) ของ name servers ที่ resolve ชื่อไม่ได้ · เป็นฟังก์ชันสำคัญมาก อินเทอร์เน็ตทำงานไม่ได้ถ้าไม่มี · DNSSEC ให้ความปลอดภัย (authentication, message integrity) · ICANN (Internet Corporation for Assigned Names and Numbers) ดูแล root DNS domain · มี 13 logical root name "servers" ทั่วโลก (ชื่อ a.root-servers.net ถึง m.root-servers.net) แต่ละ "server" ถูก replicate หลายชุด
    Top-Level Domain (TLD) servers
    รับผิดชอบ .com, .org, .net, .edu, .aero, .jobs, .museums และ country domains ทั้งหมด เช่น .cn, .uk, .fr, .ca, .jp · Network Solutions: authoritative registry ของ .com, .net · Educause: .edu TLD
    Authoritative DNS servers
    DNS server ขององค์กรเอง ให้ hostname-to-IP mappings แบบ authoritative สำหรับ host ที่มีชื่อขององค์กร · องค์กรดูแลเองหรือให้ service provider ดูแลก็ได้
    Local DNS name servers
    เมื่อ host ส่ง DNS query จะไปที่ local DNS server ก่อน ซึ่งตอบจาก local cache ของคู่ name-to-address ล่าสุด (อาจล้าสมัย!) หรือส่งต่อ request เข้าไปใน DNS hierarchy · ISP แต่ละรายมี local DNS server (ดูของตัวเองได้ด้วย scutil --dns บน MacOS หรือ ipconfig /all บน Windows) · local DNS server ไม่ได้อยู่ใน hierarchy โดยตรง

    DNS name resolution: iterated query vs recursive query

    ตัวอย่าง: host ที่ engineering.nyu.edu ต้องการ IP address ของ gaia.cs.umass.edu โดยมี local DNS server คือ dns.nyu.edu และ authoritative DNS server คือ dns.cs.umass.edu

    Iterated query

    server ที่ถูกถามตอบกลับด้วยชื่อ server ที่ควรไปถามต่อ — "I don't know this name, but ask this server" local DNS server จึงเป็นผู้วนถาม root → TLD → authoritative เอง

    Recursive query

    ผลักภาระการ resolve ชื่อไปให้ name server ที่ถูกถาม ซึ่งไปถามต่อเองเป็นทอดๆ แล้วส่งคำตอบย้อนกลับ

    คำถามในสไลด์: จะเกิด heavy load at upper levels of hierarchy?

    Caching DNS information และ DNS records

    • เมื่อ name server (ตัวใดก็ได้) เรียนรู้ mapping แล้วจะ cache ไว้ และตอบ query ถัดไปด้วย mapping ที่ cache ทันที → ปรับปรุง response time
    • cache entries หมดอายุ (หายไป) หลังเวลาหนึ่งเรียกว่า TTL · local name servers มักจะ cache TLD servers ไว้
    ข้อควรระวัง: cache อาจล้าสมัย

    ถ้า host ที่มีชื่อเปลี่ยน IP address อินเทอร์เน็ตทั้งหมดอาจยังไม่รู้จนกว่า TTL ทั้งหมดจะหมดอายุ — DNS จึงเป็น best-effort name-to-address translation

    • DNS cache poisoning

    Main challenges

    bandwidth จาก server ถึง client เปลี่ยนไปตามเวลา ตามระดับ congestion (ในบ้าน, access network, network core, video server) และ packet loss / delay จาก congestion ทำให้เล่นช้าหรือคุณภาพวิดีโอแย่

    • continuous playout constraint: ระหว่างเล่นวิดีโอ timing ต้องตรงกับต้นฉบับ แต่ network delay แปรผัน (jitter) จึงต้องมี client-side buffer
    • ความท้าทายอื่น: client interactivity (pause, fast-forward, rewind, jump) และ video packets อาจหายและถูกส่งซ้ำ

    Playout buffering: ส่งวิดีโอด้วย constant bit rate → เดินทางผ่าน variable network delay → client รับ → เล่นด้วย constant bit rate หลังจาก client playout delay โดยพักข้อมูลใน buffer เพื่อชดเชย network-added delay และ delay jitter

    server

    • แต่ละ chunk เข้ารหัสไว้หลาย rate (เช่น 360p, 720p, 1080p, 4K)
    • แต่ละ rate เก็บเป็นไฟล์แยก และ replicate ไว้ใน CDN nodes ต่างๆ

    client
    • ประเมิน bandwidth จาก server ถึง client เป็นระยะ
    • อ่าน manifest แล้วขอทีละ chunk — เลือก coding rate สูงสุดที่ bandwidth ปัจจุบันรับไหว
    • เลือก rate ต่างกันในแต่ละช่วงเวลาได้ และขอจาก server ต่างกันได้

    "intelligence" อยู่ที่ client — client ตัดสินใจเองว่า (1) เมื่อไรจะขอ chunk (ไม่ให้ buffer ว่าง/ล้น) (2) ขอ encoding rate ไหน (คุณภาพสูงขึ้นเมื่อ bandwidth มากขึ้น) (3) ขอจากที่ไหน (URL server ที่ "ใกล้" client หรือมี bandwidth สูง)

    ความท้าทาย: จะสตรีมเนื้อหา (ที่เลือกจากวิดีโอนับล้าน) ไปยังผู้ใช้หลายแสนคนพร้อมกันได้อย่างไร?

    • single point of failure
    • point of network congestion
    • เส้นทางยาว (และอาจ congested) ไปยัง client ที่อยู่ไกล

    unreliable datagram

    TCP socket

    Application Example ที่ใช้ทั้งสองแบบ

    1. client อ่านบรรทัดตัวอักษร (data) จาก keyboard แล้วส่ง data ไปยัง server
    2. server รับ data แล้วแปลงตัวอักษรเป็นตัวพิมพ์ใหญ่
    3. server ส่ง data ที่แก้แล้วกลับไปให้ client
    4. client รับ data ที่แก้แล้วและแสดงบรรทัดนั้นบนหน้าจอ

    • ผู้ส่งแนบ IP destination address และ port # ไปกับทุก packet เอง
    • ผู้รับดึง IP address และ port# ของผู้ส่งออกมาจาก packet ที่ได้รับ

    เลือกคำตอบให้ครบแล้วกด "ตรวจคำตอบ" ด้านล่าง ระบบจะเฉลยพร้อมคำอธิบายทุกข้อ

    01สถาปัตยกรรมใดมีเซิร์ฟเวอร์เป็น always-on host และ permanent IP?

    Client-Server: เซิร์ฟเวอร์เป็น always-on host มี permanent IP address มักอยู่ใน data center · ส่วน P2P ไม่มีเซิร์ฟเวอร์ส่วนกลางที่เปิดตลอดเวลา

    02คุณสมบัติเด่นของ P2P คือข้อใด?

    P2P มี self-scalability — peer ใหม่เพิ่มทั้งความสามารถให้บริการและความต้องการใช้บริการ · ไม่มีเซิร์ฟเวอร์ส่วนกลางที่เปิดตลอดเวลา และ IP เปลี่ยนได้ตลอดจึงจัดการซับซ้อนกว่า

    03"Process" หมายถึงอะไร?

    Process คือโปรแกรมที่รันอยู่บนโฮสต์

    04โปรเซสในเครื่องเดียวกันสื่อสารกันด้วยกลไกใด?

    โปรเซสในเครื่องเดียวกันคุยกันผ่าน Inter-Process Communication (IPC) ที่ OS ควบคุม · ส่วนโปรเซสต่างเครื่องคุยกันด้วยการแลกเปลี่ยนข้อความ (messages)

    05เหตุใด IP address อย่างเดียวไม่พอระบุตัวตน process?

    IP address ระบุได้แค่ระดับเครื่อง/โฮสต์ แต่เครื่องเดียวรันได้หลายโปรเซสพร้อมกัน จึงต้องใช้คู่ IP address + Port number (IP = บ้านเลขที่, Port = หมายเลขห้อง)

    06Socket เปรียบเสมือนอะไร?

    Socket คือจุดที่ process ส่ง/รับข้อความ เปรียบเหมือนประตู · แอปควบคุมสิ่งที่อยู่เหนือ socket ส่วน OS ควบคุม transport, network, link, physical ที่อยู่ใต้ลงไป

    07ข้อใด "ไม่ใช่" สิ่งที่ TCP รับประกัน?

    TCP ให้ reliable transport, flow control, congestion control และเป็น connection-oriented แต่ไม่รับประกัน timing, throughput ขั้นต่ำ และ security

    08UDP ต่างจาก TCP อย่างไร?

    UDP เป็น unreliable data transfer — ไม่มี reliability, flow control, congestion control, timing, throughput guarantee, security หรือ connection setup ใดๆ

    09Web documents (HTTP) ใช้ transport protocol ใด?

    web → HTTP → TCP · client เปิด TCP connection ไปยัง server ที่ port 80

    10เกม interactive มักใช้ transport protocol ใด?

    ตาราง app ↔ transport: interactive games → UDP หรือ TCP · SMTP และ FTP เป็น application-layer protocol ไม่ใช่ transport protocol

    11TLS ทำหน้าที่อะไร?

    TLS เข้ารหัสการเชื่อมต่อ TCP ให้ data integrity และ endpoint authentication · ทำงานที่ application layer (แอปเรียกใช้ TLS library ซึ่งใช้ TCP อีกที) จึงไม่ได้แทนที่ TCP

    12HTTP ย่อมาจากอะไร อยู่ชั้นใด?

    HTTP = HyperText Transfer Protocol เป็น application-layer protocol ของเว็บ

    13"HTTP is stateless" หมายความว่าอย่างไร?

    Stateless: เซิร์ฟเวอร์ไม่เก็บข้อมูลหรือจดจำประวัติคำขอในอดีตของ client เลย — ระบบง่าย แต่ถ้าต้องการจดจำสถานะต้องพึ่งกลไกอื่น เช่น cookie

    14Non-persistent HTTP คือข้อใด?

    Non-persistent: เปิด TCP connection → ส่งได้อย่างมาก 1 object → ปิด ถ้ามีหลาย object ต้องเปิด-ปิดใหม่ทุกครั้ง · ข้อ A คือ Persistent HTTP

    15สูตรเวลาตอบสนองของ Non-persistent HTTP?

    1 RTT สำหรับเปิด TCP connection + 1 RTT สำหรับส่งคำขอและรับ byte แรก + เวลาส่งไฟล์ = 2RTT + file transmission time

    16Persistent HTTP (1.1) ดีกว่า Non-persistent อย่างไร?

    Persistent HTTP (HTTP/1.1) เปิด TCP connection ค้างไว้ ส่งหลาย object ผ่าน connection เดียว client ส่งคำขอทันทีที่เจอ object ที่อ้างอิง เหลือประมาณ 1 RTT สำหรับทุก object รวมกัน

    17Method ใดส่งข้อมูลฟอร์มไปเก็บใน entity body?

    POST ส่งข้อมูลจากฟอร์มของผู้ใช้ไปเก็บใน entity body · GET แนบ user data ไปกับ URL (หลัง '?')

    18Method ใดขอแค่ header โดยไม่โหลดไฟล์จริง?

    HEAD ขอแค่ header กลับมา โดยไม่โหลดไฟล์เนื้อหาจริง · PUT อัปโหลด/แทนที่ไฟล์บนเซิร์ฟเวอร์ด้วยเนื้อหาใหม่

    19รหัสสถานะใดหมายถึง "ค้นหาไม่พบ"?

    404 Not Found = ไม่พบไฟล์ · 200 สำเร็จ · 301 ย้ายถาวร (มี URL ใหม่ใน header) · 505 เซิร์ฟเวอร์ไม่รองรับเวอร์ชันที่ client ร้องขอ

    20เว็บเพจประกอบด้วยอะไร วัตถุแต่ละชิ้นระบุที่อยู่ด้วยอะไร?

    เว็บเพจประกอบด้วย objects หลายชิ้น (HTML file, รูปภาพ, CSS/JS, สื่ออื่นๆ) แต่ละชิ้นระบุด้วย URL และอาจอยู่คนละเซิร์ฟเวอร์ เช่น base HTML จาก server ตรง รูปจาก CDN ฟอนต์จาก Google
